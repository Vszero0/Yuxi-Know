## 1. 认识规范文件和项目

### 1.1 这些文件是谁看的

**团队/Agent 流程。** `AGENTS.md` 是仓库给 AI 编程助手提供的项目指引；`CLAUDE.md` 面向另一类助手。文件名不妨碍人阅读：它们把团队认为重要的边界、检查和协作方式写了下来。此版本两份根目录文件内容相同，不需要重复背两遍。

根规范面向整个仓库。改 `backend/` 时还要读后端规范，改 `frontend/` 时还要读前端规范，改 `docs/` 时还要读文档规范；子目录文件是补充。这里的 `NOTE/` 是个人笔记目录，`docs/AGENTS.md` 的规则可作为学习材料，不应误认为它自动管辖 `NOTE/`。

### 1.2 为什么不能一上来读完所有资料

**团队/Agent 流程。** 改一个错别字，通常看根规则和直接相关文件就够；改权限、数据库、持久化或多个模块，就需要读架构与相关专题。提交代码或创建 PR（合并请求）前要看贡献指南；多分支、长期数据复用或数据库结构不兼容时，还需关注隔离运行环境。项目也写明当前用户的明确要求优先。

这是按风险加载信息：看太少容易漏约束，看太多则难以找到本次真正相关的信息。具体读取顺序是本项目工作流程，不意味着复杂改动可以省略对影响范围的调查。

### 1.3 先认清系统边界

Yuxi 的网页由 Vue 制作，后端主要使用 FastAPI；后台有独立 worker 和多个存储组件。Docker Compose 描述这套开发环境有哪些服务、怎样连接，见 [docker-compose.yml](../docker-compose.yml)；[ARCHITECTURE.md](../ARCHITECTURE.md) 是系统地图。文档能帮助定位，但想知道具体函数做了什么，还应看当前源码。

**学习例子：**如果你要修改聊天页面，先确定是按钮样式、发送请求，还是后端处理出错；这三种问题虽然都在聊天功能中，可能属于完全不同的位置。

## 2. 动手之前：需求、范围与设计

### 2.1 目标、非目标与验收

**通用经验。** “把首页改好”太模糊：什么叫好？哪些内容必须保留？如果没有约定，开发者做完也可能不是用户想要的。

假设需求是“列表为空时显示提示”：

- **目标**：没有数据时显示“暂无内容”。
- **非目标**：不重新设计整个页面，也不修改数据接口。
- **验收**：空列表能看到提示；有数据时正常显示列表；加载失败时显示错误而不是“暂无内容”。

目标说明要达到什么；非目标说明哪些事情不属于当前工作；验收是可观察的判断标准。多步任务再按步骤列出验证方式，而不是只列“修改代码”。

### 2.2 先走通最小完整流程，再决定怎么改

**通用经验。** 在设计前分清：用户明确要求什么，现有系统有什么约束，哪些想法只是开发者自行添加的。先查现有功能能否完成，再决定是否新增代码。

**假设例子：**用户只要求能导出一份报表；先确认现有下载接口能否满足，而不是立刻增加报表中心、权限系统和任务调度器。最小完整流程也要覆盖真正需要的错误处理，并非只做一个演示按钮。

根规范中的“例如”“也可以”通常表示方向，不是无限扩展需求的授权。出现会改变结果、数据、权限或外部行为的歧义时，应说清候选解释并确认；小的实现选择则可以记录假设、继续推进。

### 2.3 职责归属、接口承诺和复用

**通用经验。** 一个功能应放在真正负责该业务的地方：不能因为某个页面第一个使用它，就把所有业务规则塞进页面。**接口契约**是其他调用者对该功能输入、输出和行为的合理依赖。

例如，多个页面都查询同一知识库权限时，权限判断更适合由负责知识库访问的后端逻辑统一处理。复用已有接口前，要确认它原本承诺什么、谁在调用，不能为了一个新页面悄悄改变所有人的结果。

规范里的“删除新机制会破坏哪个真实需求”是一种自检：若删掉新抽象、新配置或新分支后，现有需求仍都满足，说明它可能没有必要。不是反对抽象，而是避免为了可能永远不会出现的未来增加负担。

### 2.4 事实负责人、证据和拒绝后果

根规范把一条重要主张放在三个位置理解：**事实由谁负责，怎样证明，发现错误时谁能阻止进入项目**。

**假设例子：**“用户名不能重复”：

1. 数据库约束或负责写入的业务代码承载规则，是事实的主要归属（Owner）。
2. 测试同时发起或重复提交相同用户名，检查结果和最终数据；测试中的预期不能依赖被测代码自己宣称正确。
3. 自动检查或审查者发现测试失败时，拒绝合并，而不是把报告当装饰。

**Oracle（测试判定依据）**就是用来判断结果对错的标准；可以是人工明确写出的预期、独立计算结果或真实外部事实。这个例子讲的是设计方法，不是断言 Yuxi 的用户名规则。

### 2.5 范围、决策与临时计划

**通用经验 + 项目约定。** 只改完成需求需要的部分。修按钮时顺手格式化整个无关目录，会让审查者难以区分真正的修改，也可能引入新问题。发现旧问题可以说明，但不要未经要求大规模清理。

本项目要求非平凡变更记录决策：写问题、选择、可行替代项、后果与验证；被 Git 跟踪（tracked）意味着这份记录可以随仓库版本保存。`docs/vibe/` 是被忽略的临时计划，不是长期事实的唯一保存处。是否需要决策记录取决于实际变更及项目规则；本篇个人学习笔记不是新的架构决策。

## 3. 代码如何分工

### 3.1 从点击按钮到保存数据

先区分三层：**前端**是用户看见并操作的界面；**后端**处理请求和业务规则；**数据库**负责按数据模型保存记录。浏览器通常通过 HTTP 请求和后端通信；API 是这些请求入口及其约定。

在 Yuxi 的后端规范里：

```text
HTTP Router（路由） → Service（业务流程） → Repository（数据访问） → 数据库
```

- **Router**：接收 HTTP 请求、解析数据、应用认证依赖、确定状态码和响应。
- **Service**：组织完成某个业务需要的步骤和规则。
- **Repository**：集中处理数据的查询和写入。

一个模块的入口可在 [系统路由](../backend/yuxi/api/routers/system.py) 找到；这只是阅读入口，不表示其中所有功能都经过本文验证。

### 3.2 内部网页接口与 Public API

**Yuxi 约定。** Public API 是明确提供给外部调用者的接口。项目要求只有用户明确要求时才扩展对外协议；网页内部功能放对应业务路由，不能因为已有一个 Public 会话接口就顺手增加公开能力。

原因是公开接口一旦有外部程序依赖，字段、鉴权、兼容性和错误行为就形成承诺。新增一个看似方便的地址，可能意味着以后升级都要维护它。一般项目也应区分内部实现和对外承诺，但目录和发布规则各不相同。

### 3.3 统一来源，不制造互相冲突的答案

**通用经验。** Owner 在此可理解为“负责某项事实及其修改规则的主要组件”。例如，一个任务是否完成，不应由多个组件各自维护一份互不协调的最终结果；否则一个页面显示成功，另一个显示失败时就不知道信谁。

**Yuxi 约定。** 项目规定 PostgreSQL 保存会话、运行、权限和业务终态等持久事实；Redis/ARQ 用于投递、短期事件和缓存。运行状态、租约和最终输出由指定的 repository/service 维护，而不是每个调用者自行拼一套状态。它是本项目的设计，不意味着 Redis 在所有系统里都不能保存重要数据。

## 4. 数据、队列与系统可靠性

### 4.1 持久化、事务与提交顺序

**持久化**是把数据保存到能在进程重启后继续读取的存储中。**事务**是一组数据库操作的整体：成功时提交，失败时通常回滚；事务只保证其覆盖范围内的操作，不自动让数据库和外部服务成为一个原子整体。

Yuxi 规定普通输入先保存到 PostgreSQL，在相关事务提交后才向 ARQ 投递任务。这样 worker 不会因为通知过早而查不到还没提交的数据。注意：提交后投递也可能失败；这种故障仍需恢复机制，先后顺序本身不保证任务永不丢失。[调度服务](../backend/yuxi/modules/agents/services/scheduler.py)中的 `dispatch_next_input`、`deliver` 和 `recover_pending_dispatches` 是进一步阅读的入口。

如果一个业务操作要修改多处数据库记录，规范要求有一个**事务 Owner**负责整体提交或回滚，避免每层各自提交、导致一半成功一半失败。

### 4.2 线程、输入、轮次和执行不是同一个东西

**Yuxi 约定，简化理解。** 一次聊天可能有以下几种身份：

- **Thread**：会话或对话，用于组织历史。
- **Input**：一次提交的输入，保留其独立身份。
- **Receipt**：接收回执，用于记录一次接收及相关幂等事实。
- **Turn**：一轮用户请求及其最终结果的业务单位。
- **Run**：执行的一段运行；等待人工处理后恢复等情况可能使同一轮有不止一段 Run。
- **Message / artifact**：消息 / 生成的文件或其他交付产物。

因此项目要求最终输出由该轮明确指向的顶层 Run 确定，`result_run_id` 记录它的身份。这里的“顶层”可以先理解为负责主任务结果的运行；协作子任务有自己的运行，不能把子任务的结果直接猜成主任务最终答案。Run 的输出、事件、产物和错误也绑定同一 Run。具体关系请以 [架构文档](../ARCHITECTURE.md) 和源码为准。

### 4.3 排队、插队和取消要指定对象

**Yuxi 约定。** FIFO 是“先进先出”。同一用户、应用、Agent 和 Thread 的普通 follow-up（后续消息）按 FIFO 单条派发；steer（转引导输入）优先，并在消费时按项目规则合并连续就绪的前缀。运行中只能在安全边界接管；等待回答或审批时禁止普通消息，协作等待只接受 FIFO 输入。取消或转引导操作针对指定的待处理 Input。

要理解这些限制，可以想象一个人在执行长任务时又收到多条补充消息：系统必须说清哪个先处理、什么时候允许改变方向、取消的是哪条消息。**连续就绪的前缀**可以先理解为按顺序排在本次可处理队伍开头、彼此连续且已经满足处理条件的一组 steer；碰到不属于这一组或尚未就绪的输入，就不能把后面的内容随意跨过去拼入。**安全边界**是运行预留的可交接时点，不是模型说到任意一个字都能立即切换；项目架构文档列举了工具批次与 checkpoint 等边界。若这些规则含糊，容易漏消息、错取消输入，或将不同请求混成一个。以上只是帮助理解的简化说明，具体实现应对照当前源码和测试。

### 4.4 租约、心跳和崩溃恢复

**通用问题，Yuxi 的具体处理属于项目约定。** 程序领取任务后可能突然退出。系统怎样知道任务仍有人处理？

- **Owner**：当前负责执行的 worker 或执行者。
- **Lease（租约）**：在一定时间内声明执行权；不是永久锁。
- **Heartbeat（心跳）**：执行者定期报告仍在工作，按规则续租。
- **终态**：成功、失败、取消等已经结束的状态；**非终态**表示仍未结束。

如果长时间没有心跳，租约失效后系统需要按自己的恢复规则给出可观察结局。项目要求非终态 Run 有明确执行负责人及租约、心跳或等价机制；这不等于所有崩溃都能自动无损恢复。相关阅读入口是 [runner.py](../backend/yuxi/modules/agents/services/runner.py)。

### 4.5 存活、就绪和业务成功是三件事

**Yuxi 约定。** `/api/system/health` 的 liveness 表示进程能响应；`/api/system/ready` 的 readiness 表示满足接收流量的前置条件。就算 ready，也还需要真实业务链路测试才能判断聊天、权限或文件操作是否正确。

好比餐厅“灯亮着”、“厨房准备好接单”和“这道菜已正确送到桌上”是不同事实。核心依赖不可用时不能冒充已就绪；可选功能可以降级，但要能看出哪个组件、什么原因以及影响了什么能力。可从 [系统路由](../backend/yuxi/api/routers/system.py)和[就绪检查](../backend/yuxi/modules/system/readiness.py)继续阅读。

### 4.6 Checkpoint、数据结构和升级

**Checkpoint（检查点）**可以理解成任务执行到某处时保存的状态，供后续读取或恢复。**Yuxi 约定** LangGraph 的 checkpoint 只使用 PostgreSQL，不提供悄悄切换到本地存储的降级路径。这样约束的是本项目的一致性与运行边界，不是所有 Agent 框架都必须用 PostgreSQL。

**Schema（结构约定）**描述数据表和字段等结构。对已有数据做 Schema 演进时，项目要求操作可重复、能处理现有数据并用真实 PostgreSQL 测试；若操作不可逆，要说明数据影响。不能只在空数据库上试一次就假定旧数据升级也安全。

### 4.7 功能关闭不等于删数据

**Yuxi 约定。** 默认部署包含知识库、图谱和评估。显式关闭 Knowledge 时，启动、路由、能力发现和 worker 的装配要一致，同时保留代码和已有数据；Agent 的知识库读取通过 MCP，需检查当前用户权限与会话选择的交集。附件解析器按需加载，避免未使用相关能力时也强行装配。

通用启发是：一个开关应该定义清楚它影响哪些入口、后台任务和数据。关闭某能力不应悄悄变成删除用户数据。

## 5. 安全与权限

### 5.1 认证和授权：你是谁，你能做什么

**认证**确认请求来自哪个身份；**授权**判断该身份能不能操作目标资源。你登录了系统，不自动意味着可以查看所有用户的文件。

**通用经验。** 隐藏按钮或拦截页面导航（前端路由守卫）可以改善体验，但用户仍可直接向后端发送请求。安全检查需要在后端进行，并针对当前用户和具体资源验证。提示词要求模型“不要访问别人文件”、不在接口说明展示某字段，也不能代替真正授权。

**假设例子：**普通用户发送删除他人文件的请求，后端应拒绝，并确认文件仍存在。管理员合法删除则应能按规则完成。页面隐藏按钮是额外的体验保护，不是没用，只是不构成最终边界。

### 5.2 哪些输入不能直接信任

**通用经验。** 来自 HTTP 请求、用户路径、配置、数据库历史内容、外部进程、网络协议、模型和工具 JSON 的值，都可能不满足预期。**解析器（parser）**把输入转为程序可处理的数据；**信任边界**是数据进入另一权限或处理范围的位置。

项目要求在真正的输入边界校验，并在产生实际操作的执行器或数据访问处再次执行授权。比如“用户选择文件”的页面只提供初步路径；真正打开文件前还必须检查它是否属于允许访问的范围。

不必把每个内部值都当成敌人反复检查，但也不能误认为 Python 类型标注会自动在运行时验证所有值；是否已有可靠保证，必须看真实调用和实际校验。

### 5.3 Fail closed：不能确认有权时，不要放行

**通用经验。** `fail-closed` 指安全检查出错或无法确认权限时，默认拒绝相关受保护操作，而不是把错误解释成“应该允许”。

**假设例子：**权限服务暂时不可用时，读取他人私有文档应失败并显示适当错误；不能为了让页面继续工作就返回全部文档。普通、无权限要求的功能是否还能继续，则要按实际设计判断。

### 5.4 路径和 URL 不能混为一谈

**Yuxi 约定。** 沙盒虚拟路径、对象存储 URL 和宿主机路径处于不同空间。例如 `/home/user/workspace/...` 可以是沙盒内路径；它不是自动等于 Mac 上的同名目录。对象 URL 是资源访问地址，也不是本地文件路径。

把用户输入的路径直接拼接使用，可能误读工作区外的文件。项目要求在负责文件系统的真实边界校验路径和权限。**沙盒**是限制程序运行范围的环境；它能降低风险，但不能代替对路径和用户身份的检查。

### 5.5 一次性密钥、重试与撤销

**通用问题，细节属于 Yuxi 约定。** 假设服务器成功创建了 API Key（接口凭据），但网络断开，用户没收到响应；如果用户重试，系统要怎样避免多创建一把、又能让请求得到一致结果？这与**幂等**有关：同一请求重试时，最终效果应符合约定，不产生意外重复。

项目进一步要求：一次性密钥要能通过幂等请求安全重放；如果密钥已撤销，要有足够的撤销记录，避免同一旧请求把密钥“复活”。**Tombstone（墓碑记录）**就是用来保留“它已删除或撤销”这一事实的记录，不等于保留可继续使用的密钥。

实际做法必须核对代码，不能从这条要求推导出应该保存明文密钥。可从 [身份安全模块](../backend/yuxi/modules/identity/security.py)和 [API Key 仓库](../backend/yuxi/modules/identity/repositories/api_keys.py)继续阅读；本文没有执行真实密钥创建或撤销。

### 5.6 秘密和运行数据不进提交

项目要求不输出或提交 `.env`、Token、账号、用户数据、运行目录和构建产物。`.env` 通常保存密钥和本机设置；Token 是调用服务或证明身份的凭据。**Git 跟踪**会把文件变更纳入版本历史，不能简单假设“后来删除文件”就等于历史里没有泄露。

示例使用占位字符串，例如 `YOUR_API_KEY`；不要把真实密钥放进文档、截图或终端输出。日志、模型提示和测试数据也可能间接包含用户内容，需要按真实场景判断。

## 6. 怎样证明改动有效

### 6.1 从用户结果出发，而不是只看成功提示

**通用经验。** API 返回 HTTP 200 说明请求得到一个成功状态码，但是否完成用户目标取决于接口契约。日志显示“完成”、AI 汇报“已修复”、模拟对象被调用一次，都不能自动证明数据库或页面真的正确。

**假设例子：**修复导出报表后，检查是否产生文件、内容是否正确、下载能否打开；再说明哪些情况没有测试。若任务只是排队，HTTP 成功可能只代表“已接收”，不能据此声称后台处理完成。

### 6.2 测试层级：小范围到真实链路

| 层级 | 一般在做什么 | 简单例子 | 不能单独证明什么 |
|---|---|---|---|
| Unit（单元） | 测较小的函数或模块 | 给权限判断函数输入几组条件 | 真实数据库、HTTP 和浏览器配合正确 |
| Integration（集成） | 测多个组件真实配合 | 通过 HTTP 请求调用 API，并检查真实数据库 | 所有前端交互和完整用户流程 |
| E2E（端到端） | 尽可能走完整用户流程 | 页面提交请求、后台处理、检查最终页面和数据 | 所有罕见故障和所有外部供应商 |

项目要求从最小相关集合开始，按风险升级：纯逻辑先做相关 unit；涉及数据库、缓存、文件时加 integration；API/权限/持久化要真实 HTTP；关键 Run、worker、队列、沙盒、恢复等应验证完整链路和最终产物。前端则有 lint、unit、build 和需要时的浏览器验证。

后端规范特别要求真实 PostgreSQL 验证并发、事务、锁、租约及 PostgreSQL 特有的 Schema 语义：替身数据库或 Python 函数测试无法自动代表真实数据库行为。测试通过只覆盖实际测试到的情况。

### 6.3 负向测试与保护规则

**Guard** 是“守卫”或保护条件，例如禁止无权限的人删除文档。负向测试不仅要产生失败，还要**因为正确的原因失败**：普通用户被拒绝，并回读资源仍存在；不能因为数据库连不上得到一个 500，就把它当成权限守卫通过。

如果要检验测试本身是否能发现问题，可以在隔离环境中暂时去掉保护、观察测试因目标缺陷失败，再恢复正确实现；不要对正在使用的真实数据做故障注入。项目要求新增 guard 有能够恢复目标缺陷的负向案例。

### 6.4 Mock、Fixture、Snapshot、Oracle

- **Mock（模拟对象）**：用可控制的替身代替真实依赖，适合验证部分逻辑；模拟成功不代表真实数据库或网络也成功。
- **Fixture（测试样本）**：测试前准备的数据或环境，例如一个用户和一篇假文档。
- **Expected output（预期结果）**：测试事先声明应该得到什么。
- **Snapshot（快照）**：记录并比较一段预期输出或界面结果。
- **Oracle（判定依据）**：用来判断结果对错的参考标准。
- **CI（持续集成）**：提交后自动运行测试、构建等检查的流程。

若 CI 一边用当前程序生成预期、一边把当前输出与刚生成的预期比较，即使程序出错也可能“自己证明自己正确”。项目要求预期、样本和快照的修改是显式且经过审阅的；但有独立预期也不自动保证它没有写错。

### 6.5 如实报告实际验证范围

项目要求在 PR（Pull Request，代码合并请求）中写实际运行的命令、结果和未执行原因；未验证不能写成通过。测试缺少依赖时，“未运行：没有可用的外部模型服务”比虚构通过有用得多。自动检查的 gate（门槛）只有在失败能阻止交付或被明确处理时，才起到保护作用。

## 7. 写出更容易维护的代码

### 7.1 先让主流程清楚，再考虑抽象

**通用经验。** 项目偏好简单、线性的主流程，避免不必要的嵌套、单次使用且没有实际意义的包装函数、静默 fallback（失败后悄悄换路径）和为了假想需求增加的配置。

但不意味着“一次调用的函数绝对不能拆”：若拆分能隔离文件写入、表达有意义的步骤或显著降低理解难度，也可以拆。相反，只是把一个表达式原样转发、没有增加语义的 helper（辅助函数）可能让读代码的人跳来跳去。

### 7.2 早返回和简单表达式

**假设例子：**函数先检查必需参数，不满足就明确返回错误；符合条件后继续主要逻辑。相比把整个函数放在多层 `if` 里，阅读时更容易看到主路径。

列表推导式和三元表达式适合简单映射或判断；多层嵌套、复杂对象组装或多步转换，明确的循环和条件往往更易读。规范不是要求把所有简洁写法都改长。

### 7.3 阅读顺序、命名和作用域

本项目要求新写或实质修改的 Python 代码尽量让公开、高层方法在前，相关方法相邻，专用细节在后，使人能从上向下读懂流程；但 Python 的基类、装饰器、默认参数和模块初始化等**定义时依赖**必须优先满足，不能为了排版破坏执行顺序。

名字尽量表达业务含义，例如 `can_read_document` 比 `check` 更明确。Python 名称开头的 `_` 常表示模块内部实现；本项目不允许跨模块导入此类私有标识，有真实共享需求时应设计公开入口。

**常量**是有稳定含义的值：跨函数共享的协议标识可以放模块级，只在一个函数使用的局部规则则留在函数内，缩小不必要的影响范围。

### 7.4 注释、异常和清理

项目要求新函数或类写简洁中文 docstring（紧跟定义的说明字符串），注释解释为什么需要某个约束、顺序或安全处理，而不是把每行代码翻译一遍。不同语义的代码段可用空行分开。

**异常**表示执行中发生错误。只有当前层能够补充稳定含义、清理资源或决定处理策略时才捕获；不要为了“程序不报错”把异常静默吞掉。可选能力降级时也要能观察到发生了什么。

改动时清理本次新引入的未使用变量、导入和分支；历史上原有的无关死代码先说明，不顺手重构。重构是改善内部结构但保持对外行为、API 契约、异常处理和异步并发语义，再用相关测试验证。小型状态或进度查询优先读取已有事实并返回最小结果，不因为简单需求重建一套事件流。

### 7.5 必需能力失败与可选能力降级

项目要求前置条件不成立时明确失败。比如核心数据库没准备好，却向外报告“系统完全就绪”，会误导调用方。可选的外部搜索服务出错时，系统可能仍能提供普通聊天，但应明确说明受影响能力；具体哪些是可选、怎样继续，取决于产品约定。

这与“有错误就整个系统退出”并不相同：重点是不要把未完成或不可用包装成成功。

## 8. 前端与文档

### 8.1 前端模块不是随处互相调用

**Yuxi 约定。** Vue 是组织用户界面的框架，Vite 用于开发和构建。项目把普通 HTTP 请求封装在 `frontend/src/apis`，组件负责页面和用户交互，不在各处自行拼接普通接口请求。

`domain` 指业务领域，例如知识库或用户；`@/` 是项目配置的源码路径别名。跨业务模块使用它公开的模块入口或公开 UI 组件，而不要直接依赖另一模块的内部 `model/` 路径。可以想成通过商店柜台办事，而不是走进对方仓库随意取货：模块内部调整时，公开入口更容易保持稳定。

视觉和交互改动要读项目的 [设计规范](../docs/develop-guides/design.md)。这是一套项目约定，并非所有 Vue 项目都必须采用相同目录。

### 8.2 不只有“有内容”这一种页面

一次页面请求至少可能经历：

| 页面状态 | 用户看到什么 | 假设例子 |
|---|---|---|
| loading | 正在加载 | 列表正在请求数据 |
| empty | 请求成功，但没有数据 | 知识库确实没有文件 |
| error | 请求或处理失败 | 网络断开、接口返回错误 |
| 断线恢复 | 连接恢复后重新获得状态 | 流式回答中连接中断后恢复显示 |

把 error 误显示成 empty，会让用户以为自己的文件不存在。**乐观 UI** 是先展示一个预计成功的效果以减少等待；它可以临时显示“正在保存”，但本项目要求最终状态以服务端/数据库事实为准，失败时不能继续假装成功。

### 8.3 一致的样式和真实页面验证

项目要求尽量复用已有 CSS 变量和 Lucide 图标，不为一次性视觉需求引入新依赖。**CSS 变量**可以统一颜色、间距和浅深色主题；**依赖**是项目引入的其他软件包。依赖有更新、体积和兼容成本，但这不等于永远不能引入新库。

界面改动不能只看代码：应在真实页面检查，按适用情况覆盖不同屏幕宽度、浅深色、加载、空状态和错误状态。**响应式**是页面能适应手机和电脑等不同尺寸，不只是把字体缩小。截图或录屏能说明当时看到的画面，但不自动证明后端数据和权限也正确。

### 8.4 正式文档的类型和事实来源

以下是 **Yuxi 的 docs/ 组织方式**，不是所有项目都必须照搬：

| 目录或材料 | 主要用途 |
|---|---|
| `intro/` | 按顺序教用户完成一个任务 |
| `advanced/` | 配置和运维参考 |
| `agents/` | Agent 配置及扩展方法 |
| `mechanisms/` | 原理、状态、权限、故障和源码定位 |
| `decisions/` | 非显然设计选择、备选方案与后果 |
| `postmortems/` | 事故经过、原因和改进 |
| changelog | 已发布的变化 |
| roadmap | 尚未完成的方向 |
| `docs/vibe/` | Git 忽略的本地临时计划 |

每个重要事实有一个主要说明位置（文档 Owner）；其他页面可以保留必要摘要和链接，不要维护多个各自独立、容易互相矛盾的完整副本。架构主链路归根 `ARCHITECTURE.md`，测试命令归测试规范，工程信任规则归对应专题。

源码、数据约束、Schema、Compose 和测试是核对当前可执行行为的重要依据；旧文档、外部 Wiki、历史 PR、AI 报告更适合作为线索。源码和测试也可能存在错误，因此应区分**项目承诺**、**代码实际行为**和**已做的验证**。

### 8.5 怎么写一篇可维护的技术文档

正式文档要先明确读者、目标、非目标和前置知识。**教程**按步骤让人完成任务；**参考文档**便于查参数和规则；机制文档解释组件、状态、权限和失败。有实质性混合时，本项目要求拆开。

调查一条真实链路时，可以从入口出发，搜索到 service / executor（真正执行操作的组件），再看 repository、持久化或事件发布，最后检查用户或模型看到什么；同时核对失败路径、权限、可选能力和测试。

项目的完整文档流程要求先规划章节，每节回答明确问题；按节完成事实与链接核对；先更新主要事实所在页面，再更新导航和引用。移动或拆分页面时，修复其他页面指向它的**入站链接**，不留两份各自维护的正文。小文案和机械链接清理可只查直接相关内容；文档改动提交前仍需项目要求的验证和独立 Review。非平凡的信息架构或长期约束变化要先建立 Git 跟踪的 proposed decision（提案决策记录）。

正式文档使用具体、可核实的现在时，写清执行者、条件、顺序、结果及失败后果；不确定时说明，未执行的验证标 `Not run`。决策原因放 decision，事故时间线放 postmortem；不把 PR 讨论和修改过程当成当前事实。已实施的 `implemented` 决策按现状描述，避免残留像未完成一样的提案待办。

不要手写容易漂移的完整 API、配置或文件清单，应链接当前源码或可生成的来源。`docs/` 站内用相对 Markdown 链接，站外公开源码用项目规定的 GitHub 链接；示例只用占位凭据和假 ID，不带真实账号、密钥、用户数据或本机绝对路径。

### 8.6 文档站构建不等于事实验证

新增正式站点页面时，项目要求在 `.vitepress/config.mts` 更新正确的导航位置；内部 Agent 指令、决策和事故复盘不会仅因放在 `docs/` 就自动进入用户导航。本站有 Agent 指令文件的字符预算，属于持续运行的自动护栏（standing-order guardrail）：超限先把背景和示例放到专题、压缩重复；确需提高要同步修改决策和检查，不能悄悄关闭检查。

文档 build（构建）能检查 Markdown、导航和链接等，但**不能证明文章中的业务解释正确**。应查相关源码和测试，再由审查者核对。遇到坏链接修链接、锚点或导航，不能仅通过扩大 `ignoreDeadLinks` 范围掩盖失败。

## 9. 协作、命令与阅读练习

### 9.1 Git、Diff、提交和审查

**Git** 记录项目文件的版本；**tracked** 文件在 Git 的版本管理范围内，**untracked** 文件尚未加入。**Diff** 是两个版本或工作区之间的差异；**commit** 是一次记录的变更；**PR（Pull Request）**是请求他人审查并合并变更的一种方式。

项目要求代码提交前由没有继承开发上下文的全新 Reviewer Agent 审查需求、差异、测试和规范，并修复实质问题。审查不仅检查“代码能跑”，还问方案是否必要、职责是否放对、有没有更简单的既有能力。测试通过能说明测试覆盖的行为，不自动说明设计是必要的。

该独立 Agent 审查方式是 **本项目的 AI 工作流程**。其他团队可能由人审查，或采用不同流程；可迁移的核心是让独立视角核对需求、代码、证据和风险。

项目要求中文 Conventional Commit：提交信息使用约定的类型前缀加简洁说明，例如假设的 `fix: 修正空列表提示`。PR 要说明受影响行为、归属、验证、风险和未验证范围。`git diff --check` 检查差异中的空白等问题；文件末尾保留一个换行，有助于工具处理。它不证明功能正确。

### 9.2 规范中的命令各是什么意思

下面是**解释原文中列出的命令，不是本笔记执行结果，也不是要求读者现在逐条执行**。命令可能需要 Docker 服务、依赖或特定工作目录。最新要求与例外以原规范和 [测试规范](../docs/develop-guides/testing-guidelines.md) 为准。

| 命令或片段 | 目的与注意点 |
|---|---|
| `python3 scripts/ci/verify_engineering_contracts.py` | 运行项目的工程约定检查脚本。 |
| `python3 -m unittest scripts.ci.test_verify_engineering_contracts` | 测试上述检查脚本自身。 |
| `docker compose exec api uv run --no-sync --group test pytest test/unit -m "not slow"` | 在运行中的 `api` 容器里，通过 `uv` 运行不标记 slow 的后端单元测试；并不代表集成和端到端测试已通过。 |
| `(cd backend && uv run ruff check yuxi)` | 在 backend 目录运行 Ruff 静态检查。括号内先切换工作目录；Ruff 是 Python 检查工具。 |
| `(cd backend && uv run ruff format yuxi --check)` | 检查代码格式，`--check` 表示检查而非直接格式化。 |
| `(cd backend && uv run ruff check --select I yuxi)` | 检查导入语句排序。Ruff 属于后端 dev 依赖组，项目说明只装 test 组的 API 镜像不用于运行它。 |
| `docker compose exec frontend pnpm run lint:check` | 在 frontend 容器做只读静态检查。`lint:check` 是检查门槛；项目的 `lint` 允许自动修复，因此可能修改文件。 |
| `docker compose exec frontend pnpm run test:unit` | 在 frontend 容器运行前端单元测试。 |
| `docker compose exec frontend pnpm run build` | 在 frontend 容器构建前端，检查能否打包。 |
| `cd docs && pnpm run build` | 在 docs 目录构建文档站；这是 `docs/` 规范中的命令，不表示本篇 NOTE 已构建。 |
| `git diff --check` | 检查 Git 差异中的空白等补丁问题；不检查未跟踪文件的完整内容，也不验证业务行为。 |

根规范的最低测试表还规定：文档/导航变更检查相对链接与文档构建；公开行为变化要结合代码验证。后端和前端各自列有额外检查。实际修改时应按受影响范围阅读对应规范，不能只照抄这张学习表。

### 9.3 三个练习：怎样把规范用起来

**练习一：空列表。** 需求是列表为空时显示提示。请回答：loading、empty、error 有什么区别？若接口失败却显示空状态，用户会误解什么？在真实页面怎样验证？

**练习二：删除权限。** 普通用户在网页上看不到删除按钮。如果他直接调用接口，后端应该验证什么？正向和负向测试分别检查什么？怎样确认文件真的没被删？

**练习三：后台处理。** 用户提交文档后，页面先显示“已接收”，几分钟后才有解析结果。为什么接收成功不等于解析成功？数据库提交后投递队列可能在哪一步失败？当 worker 崩溃，状态该如何被观察和处理？

三个例子都是教学场景，不能当成对当前 Yuxi 已经做过的实验。

### 9.4 建议的继续阅读顺序

1. 先看 [README](../README.md) 和 [项目架构](../ARCHITECTURE.md)，认识主要服务。
2. 结合 [个人项目学习笔记](个人知识库与智能体项目学习笔记.md) 的 Docker 与对话部分，理解一个请求需要哪些组件。
3. 按“前端 → API → service → repository → worker → 结果”追一条具体操作；不理解时回本笔记查术语。
4. 阅读对应的 [Agent 运行时机制](../docs/mechanisms/agent-runtime.md) 或 [知识库机制](../docs/mechanisms/knowledge-base.md)，再看相关测试。
5. 最后再读 [工程测试规范](../docs/develop-guides/testing-guidelines.md) 和项目其他细则；不要把尚不熟悉的规则硬背下来。

## 10. 术语表

遇到没见过的词先回来看，不必一次记住。相同术语在不同系统里可能有不同细节。

| 词 | 入门理解 |
|---|---|
| 前端 / 后端 | 用户操作的界面 / 处理请求和业务规则的服务端程序。 |
| HTTP / API / 路由 | 网络请求协议 / 功能入口及约定 / 根据请求地址和方式选择处理函数。 |
| 状态码 200 / 409 / 500 | 常用于表示成功 / 冲突 / 服务器错误；具体含义仍看接口契约。 |
| 请求 / 响应 | 调用方发出的信息 / 服务端返回的信息。 |
| 认证 / 授权 | 确认身份 / 判断该身份对目标操作是否有权限。 |
| 数据库 / PostgreSQL | 保存和查询数据的系统 / 本项目使用的关系型数据库。 |
| Redis / ARQ | 本项目用于缓存、短期事件等的组件 / 用 Redis 支持后台任务的工具。 |
| Worker / 队列 | 执行后台工作的程序 / 保存或传递待处理工作的机制。 |
| 事务 / commit point | 一组数据库操作的提交单位 / 事务正式提交生效的时点。数据库事务提交与 Git commit 是两个不同概念。 |
| 持久化 / 缓存 | 保存可在进程重启后读取的事实 / 为加快访问保存的可再获取或短期数据。具体持久性取决于系统配置。 |
| 幂等 / 并发 | 同一操作重试多次时最终效果符合一次的约定 / 多个操作在时间上重叠。 |
| 锁 / lease / heartbeat | 控制并发访问的机制 / 有时限的执行权声明 / 定期证明执行者仍在工作。 |
| FIFO / follow-up / steer | 先进先出 / 后续普通输入 / 引导运行改变方向的输入；具体规则属于 Yuxi。 |
| Thread / Input / Receipt | 会话 / 一次输入 / 该输入接收过程的回执事实；第 4.2 节有上下文。 |
| Turn / Run / Message / artifact | 一轮业务请求 / 一段执行 / 消息 / 文件等交付产物；这些名称的精确关系属于 Yuxi。 |
| checkpoint / LangGraph | 执行状态的检查点 / 用于组织 Agent 执行流程的框架。 |
| Owner / consumer | 负责某项事实或规则的组件 / 依赖或使用该能力的调用者。Owner 不一定是一个人。 |
| 契约 / Schema / 不变量 | 组件之间约定的行为 / 数据和接口的结构约定 / 运行中必须持续满足的规则。 |
| 解析器 parser / 边界 boundary | 把输入转换成可处理数据的程序 / 数据或权限跨越的检查位置。 |
| 副作用 / 外部状态 | 写文件、保存数据、发请求等会改变其他地方状态的操作 / 本函数之外的真实世界或系统状态。 |
| fail-closed | 无法确认允许时，拒绝受保护操作。 |
| fallback / 降级 | 某种能力无法使用时，使用替代路径或提供受限能力；是否允许由需求决定。 |
| Guard / 负向测试 | 限制非法操作的保护条件 / 检查不应发生的行为被正确拒绝的测试。 |
| Unit / Integration / E2E | 单元 / 集成 / 端到端测试；分别覆盖不同范围。 |
| Mock / Fixture / Snapshot / Oracle | 模拟对象 / 测试样本或环境 / 保存的预期结果快照 / 判断对错的依据。 |
| CI / gate | 自动运行检查的集成流程 / 不满足条件时阻止继续的质量门槛。 |
| Review / Reviewer / diff | 审阅变更 / 审阅者 / 文件差异。 |
| Git tracked / commit / PR | 纳入版本管理 / 一次版本记录 / 请求审查并合并变更。 |
| lint / build | 静态检查 / 将源码转换、打包成可运行或可部署产物。 |
| loading / empty / error | 加载中 / 成功但无数据 / 请求或处理失败。 |
| 响应式 / DOM | 界面适配不同设备和宽度 / 浏览器中表示网页结构的对象树。 |
| SaaS / Public API | 通过网络提供的软件服务 / 提供给外部调用者的公开接口；是否免费或兼容由具体产品决定。 |
| MCP / Skill | 连接工具服务的协议 / 提供操作说明和可选资源的能力包；可参见 [MCP 集成](../docs/agents/mcp-integration.md)与 [Skills 管理](../docs/agents/skills-management.md)。 |
| Token / secret / `.env` | 可证明身份或调用服务的凭据 / 秘密值 / 常用来保存本地环境配置的文件。模型的“token（文本单位）”是另一个含义。 |
| decision / postmortem | 设计决策记录 / 事故复盘。 |
| workflow / guardrail | 工作流程 / 用于限制错误、提供保护的规则或检查。 |
| SSE / 事件流 | 服务端通过持续 HTTP 连接推送事件的方式 / 随时间传输的一系列事件；断线恢复需要额外设计。 |
| 手动/自动验证 | 人实际操作检查 / 程序按脚本运行检查；两者都要说明具体覆盖范围。 |
