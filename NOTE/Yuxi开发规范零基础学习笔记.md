## 1. 认识规范文件和项目

### 1.1 这些文件是谁看的

`AGENTS.md` 是仓库给 AI 编程助手提供的项目指引；`CLAUDE.md` 面向另一类助手。文件名不妨碍人阅读：它们把团队认为重要的边界、检查和协作方式写了下来。此版本两份根目录文件内容相同，不需要重复背两遍。

根规范面向整个仓库。改 `backend/` 时还要读后端规范，改 `frontend/` 时还要读前端规范，改 `docs/` 时还要读文档规范；子目录文件是补充。这里的 `NOTE/` 是个人笔记目录，`docs/AGENTS.md` 的规则可作为学习材料，不应误认为它自动管辖 `NOTE/`。

### 1.2 为什么不能一上来读完所有资料

改一个错别字，通常看根规则和直接相关文件就够；改权限、数据库、持久化或多个模块，就需要读架构与相关专题。提交代码或创建 PR（合并请求）前要看贡献指南；多分支、长期数据复用或数据库结构不兼容时，还需关注隔离运行环境。项目也写明当前用户的明确要求优先。

这是按风险加载信息：看太少容易漏约束，看太多则难以找到本次真正相关的信息。复杂改动尤其需要调查影响范围。

### 1.3 先认清系统边界

Yuxi 的网页由 Vue 制作，后端主要使用 FastAPI；后台有独立 worker 和多个存储组件。Docker Compose 描述这套开发环境有哪些服务、怎样连接，见 [docker-compose.yml](../docker-compose.yml)；[ARCHITECTURE.md](../ARCHITECTURE.md) 是系统地图。文档能帮助定位，但想知道具体函数做了什么，还应看当前源码。

如果你要修改聊天页面，先确定是按钮样式、发送请求，还是后端处理出错；这三种问题虽然都在聊天功能中，可能属于完全不同的位置。

## 2. 动手之前：需求、范围与设计

### 2.1 目标、非目标与验收

“把首页改好”太模糊：什么叫好？哪些内容必须保留？如果没有约定，开发者做完也可能不是用户想要的。

假设需求是“列表为空时显示提示”：

- **目标**：没有数据时显示“暂无内容”。
- **非目标**：不重新设计整个页面，也不修改数据接口。
- **验收**：空列表能看到提示；有数据时正常显示列表；加载失败时显示错误而不是“暂无内容”。

目标说明要达到什么；非目标说明哪些事情不属于当前工作；验收是可观察的判断标准。多步任务再按步骤列出验证方式，而不是只列“修改代码”。

### 2.2 先走通最小完整流程，再决定怎么改

在设计前分清：用户明确要求什么，现有系统有什么约束，哪些想法只是开发者自行添加的。先查现有功能能否完成，再决定是否新增代码。

用户只要求能导出一份报表；先确认现有下载接口能否满足，而不是立刻增加报表中心、权限系统和任务调度器。最小完整流程也要覆盖真正需要的错误处理，并非只做一个演示按钮。

根规范中的“例如”“也可以”通常表示方向，不是无限扩展需求的授权。出现会改变结果、数据、权限或外部行为的歧义时，应说清候选解释并确认；小的实现选择则可以记录假设、继续推进。

### 2.3 职责归属、接口承诺和复用

假设知识库同时出现在聊天页和管理页，两个页面都要判断用户能否读取某个知识库。如果各自在前端写一份规则，以后管理员调整成员权限时，两份代码可能更新不一致；而且调用者可以绕过页面直接请求后端。更合理的做法是：**权限由后端负责知识库访问的业务代码统一判断**，页面负责展示可用选项。

一个模块对外答应了什么，称为**接口契约**：调用者提供什么输入，得到什么结果，什么情况会失败。例如“返回当前用户可见的知识库”就包含了用户身份和可见范围，不能为了某个页面方便而悄悄改成“返回全部知识库”。

**追问：项目怎样处理用户选中的知识库？** [visible_knowledge_bases](../backend/yuxi/modules/knowledge/services/access.py) 先按用户 ID 查询可见知识库，再与调用方的选择求交集；选择列表里填入一个无权访问的 ID，并不会因此使其进入返回结果。可以带着“权限范围从哪里来、选择又在哪里过滤”两个问题读这段代码。

复用既有接口时还要看谁在调用它。新增抽象之前，可以问：去掉这个新层，当前明确需求会少实现什么？如果答案是没有，先用现有结构更容易理解和维护。

### 2.4 事实负责人、证据和拒绝后果

一条规则要能回答三个问题：**谁负责保证它成立，怎么判断它成立，出错后谁能拦住变更？**

以教学用的“用户名不允许重复”为例：两个注册请求几乎同时到达时，如果只在应用里先查“用户名不存在”再插入，两个请求都可能查到不存在，接着都插入成功。数据库唯一约束可以在真正写入时阻止重复，即使请求并发到达也成立。应用层仍可提前检查，目的是给用户更友好的提示；最终限制交给数据库。

测试要准备两个相同用户名的写入请求，再检查最终记录及失败响应是否符合约定。测试的预期——例如“最终只存在一条记录”——叫 **Oracle，判定依据**。它由需求和规则确定，而不是让被测函数自己说“我正确”就算通过。测试失败后，持续集成或审查流程要能阻止不合格的改动进入项目，这个拦截点叫 **gate（门槛）**。

**追问：为什么既要数据库约束又要测试？** 约束是在系统运行时保护数据；测试是在代码变更时检查这条保护是否仍然存在。两者解决的是不同时间发生的问题。

### 2.5 范围、决策与临时计划

只改完成需求需要的部分。修按钮时顺手格式化整个无关目录，会让审查者难以区分真正的修改，也可能引入新问题。发现旧问题可以说明，但不要未经要求大规模清理。

本项目要求非平凡变更记录决策：写问题、选择、可行替代项、后果与验证；被 Git 跟踪（tracked）意味着这份记录可以随仓库版本保存。`docs/vibe/` 是被忽略的临时计划，不是长期事实的唯一保存处。比如决定更换消息持久化方案时，应让后来维护者能找到“为什么选它、放弃了什么、怎样验证”。

## 3. 代码如何分工

### 3.1 从点击按钮到保存数据

浏览器显示页面并接收点击；后端收到 HTTP 请求后处理业务；数据库保存需要长期保留的数据。**API** 是调用方使用后端能力时遵守的入口和约定，例如请求方法、地址、参数和返回值。

后端规范将工作划为：

```text
Router（接收请求）→ Service（组织业务）→ Repository（读写数据）→ 数据库
```

我们沿着一次提交消息的实际入口阅读：

1. [事件路由 submit_public_event](../backend/yuxi/api/routers/public_v1/agents/events.py) 接收 `POST /sessions/{session_id}/events`，读取请求体、`Idempotency-Key` 请求头，并通过 `Depends` 获取调用者上下文和数据库会话。完整路径还由上层路由前缀决定。
2. 同文件的 `submit_thread_event` 按事件类型分支；如果是普通消息，就调用 [accept_message](../backend/yuxi/modules/agents/services/inputs.py)。业务服务检查输入、请求身份和历史回执，组织接收消息的步骤。
3. 服务使用 [输入 Repository](../backend/yuxi/modules/agents/repositories/input.py) 等对象读写具体记录；后续调度再创建运行。路由最终按接口约定返回 `202` 和回执，表示接收阶段已完成，不等于模型已经回答完。

**为什么要这样分？** 未来另一个入口也要提交消息时，可以复用业务规则，而不是把整套规则复制到第二个路由。Repository 把具体查询集中起来，让业务流程不用处处展开数据库语句。读代码时先抓住从入口到结果的步骤，再点进去看每一步的细节。

### 3.2 内部网页接口与 Public API

Public API 是明确提供给外部调用者的接口。项目要求只有用户明确要求时才扩展对外协议；网页内部功能放对应业务路由，不能因为已有一个 Public 会话接口就顺手增加公开能力。

原因是公开接口一旦有外部程序依赖，字段、鉴权、兼容性和错误行为就形成承诺。新增一个看似方便的地址，可能意味着以后升级都要维护它。例如外部脚本依赖某个字段后，直接删除它就可能让脚本报错；要改变协议时，需要考虑调用者怎样迁移。

### 3.3 统一来源，不制造互相冲突的答案

同一条业务事实如果有多个互相独立的“最终答案”，就会产生冲突。例如任务结束时，数据库说失败，缓存却一直显示成功；页面应该信谁？因此系统要指定**事实负责人（Owner）**：谁负责保存某个事实、谁有权修改它，其他地方如何读取。

Yuxi 将会话、运行、权限和业务终态等持久事实交给 PostgreSQL，Redis/ARQ 用于任务投递、短期事件和缓存。看 [Run Repository](../backend/yuxi/modules/agents/repositories/runs.py) 可以找到运行状态与租约的写入；[调度服务](../backend/yuxi/modules/agents/services/scheduler.py) 则根据数据库中的待执行记录投递任务。

**缓存有什么用？** 它可以让读取更快，但需要定义何时更新或失效。缓存丢失后，持久事实仍可由数据库读取。**队列有什么用？** 它通知 worker 有任务要做；而任务身份和最终状态仍有数据库记录。这样队列消息重复或中断时，系统才有依据决定如何继续。

## 4. 数据、队列与系统可靠性

### 4.1 持久化、事务与提交顺序

**持久化**是把信息写入进程退出后仍可读取的存储。**事务**把一组数据库操作作为一个整体：正常完成时提交（commit），中途失败时回滚（rollback）。提交前的写入还不是其他独立事务应依赖的已提交事实。

顺着一次真实的消息接收，看清两个数据库事务和一次队列投递：

1. **接收事务**：[accept_message](../backend/yuxi/modules/agents/services/inputs.py) 检查幂等键和消息意图，接收 Input 和 Receipt，调用 `db.commit()`。这一步记录的是“输入已接收”，不是“执行已结束”。
2. **调度事务**：随后 [dispatch_next_input](../backend/yuxi/modules/agents/services/scheduler.py) 打开新的数据库会话、锁定 Thread；`claim_next_input` 按条件领取输入，创建 Turn 和 Run，并将被消费的输入绑定到它们。退出数据库会话上下文时，这一组操作提交；[会话管理器](../backend/yuxi/infrastructure/postgres/manager.py) 定义了提交和回滚。
3. **事务外投递**：提交成功后，`deliver` 把已创建的 Run ID 放进 ARQ 队列，worker 收到后执行。这样 worker 查数据库时，Run 已经是提交过的事实。

为什么不能把数据库提交和队列发送当成一回事？两者是不同系统：数据库提交成功后，发送队列仍可能因为连接故障失败。代码会记录投递失败，保留已提交的 `pending` Run；`recover_pending_dispatches` 后续扫描时重新核对会话身份、状态和当前 Run 归属，再用**原 Run ID**补投。对尚未领取的待处理 Input，恢复过程也会尝试重新调度。相关并发与补投例子可读 [集成测试](../backend/test/integration/services/test_agent_input_concurrency.py)。

**追问：为什么不在每一层都调用 commit？** 如果创建 Turn 的代码先提交，而绑定 Input 的代码随后失败，就会留下不完整的业务事实。事务 Owner 统一决定何时提交，可以让同一事务内的关联变更一起成功或回滚。**补投是否意味着所有执行失败都会重试？** 不意味着：补投针对符合条件的已提交 `pending` Run；执行中 worker 的租约过期走第 4.4 节的失败收敛流程。

### 4.2 线程、输入、轮次和执行不是同一个东西

沿用“用户在已有会话发送一条消息”的场景，下面这些名字分别回答不同问题：

| 对象 | 它回答的问题 | 例子 |
|---|---|---|
| Thread | 这是哪一段持续的对话？ | 用户和某个 Agent 的一个会话 |
| Input | 这次提交了什么？ | “请总结这份文档”这条输入 |
| Receipt | 这次请求是否已经被接收？ | 保存幂等键和接收结果，便于重试查询 |
| Turn | 这是哪一轮业务请求？ | 对“请总结”的一轮处理及最终结果 |
| Run | 这一轮中的哪一段执行？ | 开始调用模型的一次运行 |
| Message / artifact | 产生了什么内容或文件？ | 回答文本 / 生成的报告 |

先有 Thread；用户提交后，接收阶段保存 Input 和 Receipt；调度领取时再创建 Turn、Run 并绑定输入；Run 执行后产生消息或其他产物。同一 Turn 在等待人工回答或审批后继续，可能对应不止一段 Run，所以不能把 Turn 和 Run 当作同义词。

**为什么还需要 `result_run_id`？** 一轮工作可能有多段执行，甚至有协作子任务。要展示这轮的最终结果，系统需要明确指向负责最终结果的顶层 Run，而不是从一堆运行里猜测。代码入口见 [Turn Repository](../backend/yuxi/modules/agents/repositories/turn.py) 和 [Run 创建](../backend/yuxi/modules/agents/services/run_creation.py)。

### 4.3 排队、插队和取消要指定对象

FIFO 是“先进先出”。同一用户、应用、Agent 和 Thread 的普通 follow-up（后续消息）按 FIFO 单条派发；steer（转引导输入）优先，并在消费时按项目规则合并连续就绪的前缀。运行中只能在安全边界接管；等待回答或审批时禁止普通消息，协作等待只接受 FIFO 输入。取消或转引导操作针对指定的待处理 Input。

要理解这些限制，可以想象一个人在执行长任务时又收到多条补充消息：系统必须说清哪个先处理、什么时候允许改变方向、取消的是哪条消息。**连续就绪的前缀**可以先理解为按顺序排在本次可处理队伍开头、彼此连续且已经满足处理条件的一组 steer；碰到不属于这一组或尚未就绪的输入，就不能把后面的内容随意跨过去拼入。**安全边界**是运行预留的可交接时点，不是模型说到任意一个字都能立即切换；项目架构文档列举了工具批次与 checkpoint 等边界。若这些规则含糊，容易漏消息、错取消输入，或将不同请求混成一个。

读实现时可以从 [ready_batch](../backend/yuxi/modules/agents/repositories/input.py) 开始，注意它如何选择可领取的队头，以及遇到尚未准备好的输入时为何停止。然后回到 [claim_next_input](../backend/yuxi/modules/agents/services/scheduler.py)，看领取动作怎样与创建 Turn、Run 放在同一事务中。

**追问：为什么取消要指定 Input？** 如果用户先后排了 A、B，只说“取消一条”无法判断目标；明确身份后才能取消 B，同时保留 A 的顺序。相应例子可看 [输入并发测试](../backend/test/integration/services/test_agent_input_concurrency.py) 中 `test_cancelling_newer_input_keeps_older_queue_head_visible`。

### 4.4 租约、心跳和崩溃恢复

worker 可以理解为后台干活的进程。它领取 Run 后可能因断电、进程退出或网络中断而失联；系统不能一直把失联的任务显示为“正在运行”。

- **Owner**：当前取得这段运行执行权的 worker。
- **Lease（租约）**：执行权有效到某个时间；时间到了还没续租，原 owner 就不能继续凭旧资格操作。
- **Heartbeat（心跳）**：worker 定期报告自己仍在工作，符合条件时延长租约。

按时间看：① worker A 领取 Run，数据库记录 owner 和租约到期时间；② A 定期发送心跳续租；③ A 暂停太久，租约到期；④ A 恢复后尝试续租，[renew_lease](../backend/yuxi/modules/agents/repositories/runs.py) 检查 owner、状态及过期时间，拒绝已过期租约；⑤ 恢复流程发现过期后，[reconcile_expired_lease](../backend/yuxi/modules/agents/repositories/runs.py) 将 Run 收敛为 `failed`、记录 `worker_lease_expired`，并标记清理待处理。

**为什么不直接让另一个 worker 当作没事发生继续执行？** A 失联前可能已经调用外部工具，例如发送了一次外部请求，但还没来得及记录结果。系统无法只靠租约判断外部副作用是否发生；贸然再执行一次可能造成重复。项目把这次运行标为失败并说明结果未知，再按具体操作检查副作用。**这和 4.1 的 pending 补投有何不同？** pending 还没有成为已执行中的有效租约运行；这里讨论的是执行途中失联。心跳调用可从 [runner.py](../backend/yuxi/modules/agents/services/runner.py) 继续追踪。

### 4.5 存活、就绪和业务成功是三件事

服务部署后，调度系统需要知道：进程还在不在？它现在能否接收请求？用户的业务是否真的完成？这三个问题要分开回答。

1. **存活 liveness**：`/api/system/health` 检查进程是否能响应；用于发现需要重启的进程。
2. **就绪 readiness**：`/api/system/ready` 检查接收流量的前置条件。Yuxi 的 [readiness 实现](../backend/yuxi/modules/system/readiness.py) 包含 PostgreSQL、Redis 和兼容 worker 等探测；核心依赖没准备好时，不应把流量送来。
3. **业务结果**：例如发送一条聊天消息并最终取得正确回答。这需要走完整链路，看实际结果和持久状态。

餐厅亮灯说明店还在，厨房准备好说明可以接单，一道菜正确送到桌上才是这笔订单完成。[系统路由](../backend/yuxi/api/routers/system.py) 可以看到前两个检查入口。可选组件发生故障时，系统应让人知道受影响的能力和原因，以便判断还能提供哪些服务。

### 4.6 Checkpoint、数据结构和升级

**Checkpoint（检查点）**可以理解成任务执行到某处时保存的状态，供后续读取或恢复。项目的 LangGraph checkpoint 只使用 PostgreSQL，不提供悄悄切换到本地存储的降级路径；这样各进程读取的状态有一致的存储位置。

**Schema（结构约定）**描述数据表和字段等结构。对已有数据做 Schema 演进时，项目要求操作可重复、能处理现有数据并用真实 PostgreSQL 测试；若操作不可逆，要说明数据影响。不能只在空数据库上试一次就假定旧数据升级也安全。

**为什么升级必须用旧数据测试？** 例如新增一个不允许为空的字段，空库建表可能成功，但已有记录没有这个字段的值，直接加限制就可能失败。迁移需要先设计旧记录如何补值，再增加约束，并用已有数据状态验证。**操作可重复是什么意思？** 同一升级操作因中断而再次执行时，应有明确处理，不能盲目重复建表或破坏已迁移数据。真实 PostgreSQL 的约束、锁和事务行为应在 PostgreSQL 上验证。

### 4.7 功能关闭不等于删数据

默认部署包含知识库、图谱和评估。显式关闭 Knowledge 时，启动、路由、能力发现和 worker 的装配要一致，同时保留代码和已有数据；Agent 的知识库读取通过 MCP，需检查当前用户权限与会话选择的交集。附件解析器按需加载，避免未使用相关能力时也强行装配。

通用启发是：一个开关应该定义清楚它影响哪些入口、后台任务和数据。关闭某能力不应悄悄变成删除用户数据。

## 5. 安全与权限

### 5.1 认证和授权：你是谁，你能做什么

把系统想成有许多房间的办公楼：**认证**检查“你是谁”，**授权**检查“你能进入哪间房、能做什么”。登录成功只是确认身份；是否能读、改或删除某个知识库，还要根据当前用户与目标资源判断。

以两个用户 A、B 为例，A 在页面上看不到 B 的私有知识库；即使 A 自己构造 HTTP 请求，后端也必须在读取或修改资源时检查 A 的权限。页面隐藏按钮可以减少误操作，但真正决定是否放行的是服务端。

Yuxi 的 [知识库可见范围](../backend/yuxi/modules/knowledge/services/access.py) 先按当前用户查询可见知识库，再与会话选择求交集：用户有权看的集合是 `{A, B}`，本次选择 `{B, C}`，最终可用的是 `{B}`。填写 C 的 ID 不会凭空获得权限。继续阅读时可以追 `get_knowledge_bases_by_uid` 的实现与调用这个服务的位置。

**怎样测删除权限？** 准备 A、B 和 B 的文件；A 发删除请求后，检查接口按约定拒绝，再重新读取确认文件仍存在。然后以有权身份执行合法操作，检查成功路径。这样既检查拒绝，也检查规则没有把所有人都挡住。

### 5.2 哪些输入不能直接信任

程序在不同位置接收数据：HTTP 请求携带参数，模型生成工具调用，用户提供文件路径，外部进程返回结果。这些值在进入当前处理流程时都需要校验：类型是否正确？是否缺字段？要操作的资源是否属于当前用户？这种数据跨入另一处理或权限范围的位置叫**信任边界**。

例如用户提交文件名 `report.txt`，程序需要确认它最终解析到允许访问的工作区内。如果输入包含 `../` 并被简单拼接，解析后的路径可能指向工作区外。应在真正打开文件的边界检查规范化后的目标路径和用户权限；前端提前检查可以提供提示，但不能代替打开文件时的检查。

**类型标注能解决吗？** Python 的 `path: str` 主要告诉开发者和检查工具预期类型，它本身不会自动证明路径安全。解析器负责将输入转换为结构化数据，业务校验和授权继续判断这个值是否允许被使用。

### 5.3 Fail closed：不能确认有权时，不要放行

`fail-closed` 的意思是：对受保护操作，如果无法确认允许，就不要放行。例如权限服务查询失败时，系统不知道当前用户是否能读取某个私有文件；正确做法是返回错误并保留可排查的信息，而不是因为查询出错就返回文件内容。

**追问：拒绝是否等于把整个网站关闭？** 不必。需要该权限判断的读取操作应拒绝；与故障无关、仍满足前置条件的功能可以根据产品设计继续工作。关键是把“检查失败”和“检查通过”分清楚。

### 5.4 路径和 URL 不能混为一谈

沙盒虚拟路径、对象存储 URL 和宿主机路径处于不同空间。例如 `/home/user/workspace/...` 可以是沙盒内路径；它不是自动等于 Mac 上的同名目录。对象 URL 是资源访问地址，也不是本地文件路径。

把用户输入的路径直接拼接使用，可能误读工作区外的文件。比如允许访问的目录是 `/workspace`，输入 `../secrets.txt` 后，规范化的目标可能已经落到工作区外。负责打开文件的组件需要先解析路径、确认目标仍在允许的目录内，再结合用户身份校验权限。**沙盒**是限制程序运行范围的环境，它提供隔离；路径和用户权限判断则决定这次操作是否被允许。

### 5.5 一次性密钥、重试与撤销

假设用户创建 API Key，服务器已经创建成功，但响应在网络中丢失了。用户不知道是否成功，于是用同一个请求重试。系统要避免再创建一把新 Key，同时还要解决：数据库通常不保存可直接取出的明文，怎样再次返回同一密钥？

Yuxi 的实现可以按这个顺序读：

1. 调用方提供请求身份和创建意图；[issue_api_key](../backend/yuxi/modules/identity/services/api_keys.py) 使用稳定的派生上下文和用户身份产生密钥。
2. [derive_api_key](../backend/yuxi/modules/identity/security.py) 使用服务端持久保存的独立派生主密钥、用户身份和幂等域，通过 HMAC 确定性派生密钥。相同输入与主密钥可重新得到相同密钥；数据库保存的是密钥哈希和前缀，而不是把明文原样存进去。HMAC 可以先理解为“用只有服务端知道的秘密，对指定输入计算稳定结果”的方法。
3. [APIKeyRepository.create](../backend/yuxi/modules/identity/repositories/api_keys.py) 在 PostgreSQL 中按请求 ID 获取事务级锁，检查用户和部门，再比较创建意图指纹（由名称、用户、权限范围等字段计算的摘要）。同一请求 ID、相同意图且未撤销，可以重放；同一 ID 配不同意图则冲突，不能把新要求误当成旧请求。
4. 撤销时保留标记 `revoked_at`，这类标记称为 **tombstone（墓碑记录）**。旧请求再次重放时，代码会发现凭据已撤销并拒绝，避免把它重新启用。如果当前主密钥不能重现历史密钥，也会拒绝安全重放。

**为什么要锁？** 两个重试可能同时到达；如果都先查到“没有记录”再各自创建，就会发生竞争。把同一请求 ID 的创建过程串起来，才能先检查已有结果再决定创建或重放。**幂等是否代表任何内容用同一个 ID 都会成功？** 不代表；同一个 ID 表示同一个创建意图，内容发生冲突时必须报错。

### 5.6 秘密和运行数据不进提交

项目要求不输出或提交 `.env`、Token、账号、用户数据、运行目录和构建产物。`.env` 通常保存密钥和本机设置；Token 是调用服务或证明身份的凭据。**Git 跟踪**会把文件变更纳入版本历史，不能简单假设“后来删除文件”就等于历史里没有泄露。

示例使用占位字符串，例如 `YOUR_API_KEY`；不要把真实密钥放进文档、截图或终端输出。日志、模型提示和测试数据也可能间接包含用户内容，需要按真实场景判断。

## 6. 怎样证明改动有效

### 6.1 从用户结果出发，而不是只看成功提示

判断改动是否完成，要从用户希望得到的结果往回看。以聊天为例：用户提交消息后先收到 HTTP `202`，这说明接口已接收输入；后台仍要领取任务、运行模型并产生最终消息。如果只看到 `202` 就宣布“回答成功”，就漏掉了后半段流程。

因此验收可以分阶段：提交后检查回执和输入记录；等待后台执行后检查 Run 终态；最后检查用户能看到的回答与预期一致。排查时也能按阶段缩小范围：没有回执先看接收，没有运行看调度，运行失败看 worker 和错误信息。实际入口见 [事件路由](../backend/yuxi/api/routers/public_v1/agents/events.py) 与 [调度服务](../backend/yuxi/modules/agents/services/scheduler.py)。

### 6.2 测试层级：小范围到真实链路

用同一个“用户发送消息并看到回答”的功能，理解三种测试为什么各有价值：

| 层级 | 怎样测试 | 回答的问题 |
|---|---|---|
| Unit（单元测试） | 单独给消息意图计算或格式化逻辑输入数据，检查输出 | 这段小逻辑在给定输入下是否正确？ |
| Integration（集成测试） | 连接真实 PostgreSQL，接收和领取输入，检查关联记录、顺序及事务结果 | 多个组件和数据库一起工作时，规则是否成立？ |
| E2E（端到端） | 从页面或真实 HTTP 入口提交，经过队列与 worker，再观察最终状态和结果 | 用户实际经过的主要流程能否走通？ |

例如 [并发集成测试](../backend/test/integration/services/test_agent_input_concurrency.py) 的 `test_concurrent_claims_consume_only_fifo_head` 检查并发领取时的队头行为；`test_recovery_republishes_committed_pending_run` 检查已提交 pending Run 的补投。它们各自针对一个可观察结果，并非只检查某个函数被调用过。

**为什么锁和并发需要真实 PostgreSQL？** 锁何时阻塞、事务何时可见，是数据库自身的行为。用 Python 假对象替代数据库时，可以快速测业务分支，却没有运行 PostgreSQL 的锁。项目因此要求并发、事务、租约及 PostgreSQL 特有结构使用真实 PostgreSQL 验证。前端还按改动运行 lint、单元测试、build，必要时在浏览器验证实际交互。

### 6.3 负向测试与保护规则

**Guard（守卫）** 是防止不符合条件的操作发生的检查，例如“用户只能删除自己有权限删除的文件”。正向测试验证有权用户可以删除；负向测试验证无权用户不能删除。

一个有意义的负向测试可以这样安排：先创建文件并确认它存在；用无权用户发删除请求；断言返回符合接口契约的拒绝结果；最后重新读取文件，确认记录和内容仍在。如果测试只看“请求失败”，数据库断连导致的 `500` 也会让它误以为权限检查起了作用。

**怎么知道测试真能发现缺陷？** 在隔离的测试环境暂时去掉目标权限检查，再运行测试：它应当因为无权操作被放行而失败；恢复检查后测试通过。项目要求为新增守卫准备能暴露目标缺陷的负向案例。

### 6.4 Mock、Fixture、Snapshot、Oracle

继续沿用“用户删除文件”的测试：

- **Fixture（测试准备）**：预先创建用户 A、用户 B 和 B 的文件，结束后清理数据。
- **Mock（模拟对象）**：用可控制的替身代替某个依赖。例如让通知服务固定返回成功，以便专心检查删除业务；如果正在测试真实数据库权限和事务，就应连接对应真实组件。
- **Expected output（预期结果）**：提前写明 A 的删除请求应被拒绝，文件仍存在。
- **Oracle（判定依据）**：这些预期来自授权规则和接口约定，是判断结果对错的标准。
- **Snapshot（快照）**：保存预期文本或界面结构，后续测试与之比较；有意改变输出时需审阅差异再更新。
- **CI（持续集成）**：自动运行约定的检查，例如测试和构建，让每次变更都经过相同门槛。

**为什么不能让程序当场生成答案，再把自己的结果与这个答案比较？** 如果程序把无权删除误判为允许，两份数据仍然一致。预期必须由需求或独立事实确定；更新 fixture、快照或预期时也要审阅“规则是否真的改变了”，不能只为了让测试变绿。

### 6.5 如实报告实际验证范围

项目要求在 PR（Pull Request，代码合并请求）中写实际运行的命令、结果和未执行原因；未验证不能写成通过。测试缺少依赖时，“未运行：没有可用的外部模型服务”比虚构通过有用得多。自动检查的 gate（门槛）只有在失败能阻止交付或被明确处理时，才起到保护作用。

## 7. 写出更容易维护的代码

### 7.1 先让主流程清楚，再考虑抽象

读代码时，理想情况是先看到主流程：检查输入、执行操作、保存结果。与业务无关的多层包装会让读者反复跳转；静默 fallback 则可能掩盖真实故障，例如数据库连接失败后悄悄换到一份本地文件，界面看似正常，用户之后却找不到数据。

抽取函数要有可读的目的：例如 `validate_access` 表示独立的权限校验步骤，`save_report` 表示明确的写入操作。反过来，如果 `do_it(x)` 只原样调用另一个函数且名字没有新增含义，读者要多跳一次却没有获得解释。判断标准是它是否让业务、边界或重复逻辑更清楚。

### 7.2 早返回和简单表达式

**早返回**是先处理不满足条件的情况，让正常路径留在较浅的缩进中。下面是教学示例，两个函数要表达同一规则：没有用户或用户无权读取时拒绝；否则返回文件内容。

```python
# 多层嵌套：主要操作被包在条件内部
def read_document(user, document):
    if user is not None:
        if user.can_read(document):
            return document.content
        else:
            raise PermissionError("无权读取")
    else:
        raise PermissionError("请先登录")
```

```python
# 先排除不满足的情况，再读主流程
def read_document(user, document):
    if user is None:
        raise PermissionError("请先登录")
    if not user.can_read(document):
        raise PermissionError("无权读取")
    return document.content
```

两种写法在这个例子里对外行为相同；后一种让读者先看到限制条件，再直接看到成功时做什么。项目里可以对照 [claim_next_input](../backend/yuxi/modules/agents/services/scheduler.py) 开头多个条件不满足时的 `return None`。列表推导式和三元表达式适合简单情况；多步转换和复杂分支使用普通循环、`if` 往往更清楚。

### 7.3 阅读顺序、命名和作用域

本项目要求新写或实质修改的 Python 代码尽量让公开、高层方法在前，相关方法相邻，专用细节在后，使人能从上向下读懂流程；但 Python 的基类、装饰器、默认参数和模块初始化等**定义时依赖**必须优先满足，不能为了排版破坏执行顺序。

名字尽量表达业务含义，例如 `can_read_document` 比 `check` 更明确。Python 名称开头的 `_` 常表示模块内部实现；本项目不允许跨模块导入此类私有标识，有真实共享需求时应设计公开入口。

**常量**是有稳定含义的值：跨函数共享的协议标识可以放模块级，只在一个函数使用的局部规则则留在函数内，缩小不必要的影响范围。

### 7.4 注释、异常和清理

项目要求新函数或类写简洁中文 docstring（紧跟定义的说明字符串），注释解释为什么需要某个约束、顺序或安全处理，而不是把每行代码翻译一遍。不同语义的代码段可用空行分开。

**异常**表示执行中发生错误。只有当前层能够补充稳定含义、清理资源或决定处理策略时才捕获；不要为了“程序不报错”把异常静默吞掉。可选能力降级时也要能观察到发生了什么。

改动时清理本次新引入的未使用变量、导入和分支；历史上原有的无关死代码先说明，不顺手重构。重构是改善内部结构但保持对外行为、API 契约、异常处理和异步并发语义，再用相关测试验证。小型状态或进度查询优先读取已有事实并返回最小结果，不因为简单需求重建一套事件流。

例如文件处理需要先打开资源再解析内容，打开失败时，上层需要知道处理没有成功；若捕获所有异常后返回空列表，页面就可能把“读取失败”误当成“文件为空”。在能补充业务错误信息的地方捕获并向上报告，资源清理可用上下文管理器或 `finally`。这样调用方既能处理失败，也不会遗漏清理。

### 7.5 必需能力失败与可选能力降级

项目要求前置条件不成立时明确失败。比如核心数据库没准备好，却向外报告“系统完全就绪”，会误导调用方。可选的外部搜索服务出错时，系统可能仍能提供普通聊天，但应明确说明受影响能力；具体哪些是可选、怎样继续，取决于产品约定。

这与“有错误就整个系统退出”并不相同：重点是不要把未完成或不可用包装成成功。

## 8. 前端与文档

### 8.1 前端模块不是随处互相调用

Vue 是组织用户界面的框架，Vite 用于开发和构建。项目把普通 HTTP 请求封装在 `frontend/src/apis`，组件负责页面和用户交互，不在各处自行拼接普通接口请求。

`domain` 指业务领域，例如知识库或用户；`@/` 是项目配置的源码路径别名。跨业务模块使用它公开的模块入口或公开 UI 组件，而不要直接依赖另一模块的内部 `model/` 路径。可以想成通过商店柜台办事，而不是走进对方仓库随意取货：模块内部调整时，公开入口更容易保持稳定。

视觉和交互改动要读项目的 [设计规范](../docs/develop-guides/design.md)。这些目录约定使项目成员能更快找到接口、组件和跨模块入口。

### 8.2 不只有“有内容”这一种页面

一次页面请求至少可能经历：

| 页面状态 | 用户看到什么 | 例子 |
|---|---|---|
| loading | 正在加载 | 列表正在请求数据 |
| empty | 请求成功，但没有数据 | 知识库确实没有文件 |
| error | 请求或处理失败 | 网络断开、接口返回错误 |
| 断线恢复 | 连接恢复后重新获得状态 | 流式回答中连接中断后恢复显示 |

把 error 误显示成 empty，会让用户以为自己的文件不存在。**乐观 UI** 是先展示一个预计成功的效果以减少等待；它可以临时显示“正在保存”，但本项目要求最终状态以服务端/数据库事实为准，失败时不能继续假装成功。

一种常见实现是分别维护 `loading`、数据和 `error`：请求开始时显示加载；成功后根据返回列表判断内容或空状态；失败时保存错误并展示重试入口。不要在 `catch` 中仅把数据置为空数组，否则页面无法区分“真的为空”和“请求失败”。对于流式回复，重连后还要按服务端保存的事实恢复展示，避免把临时画面当成最终结果。

### 8.3 一致的样式和真实页面验证

项目要求尽量复用已有 CSS 变量和 Lucide 图标，不为一次性视觉需求引入新依赖。**CSS 变量**可以统一颜色、间距和浅深色主题；**依赖**是项目引入的其他软件包，需要考虑更新、体积和兼容成本。

界面改动不能只看代码：应在真实页面检查，按适用情况覆盖不同屏幕宽度、浅深色、加载、空状态和错误状态。**响应式**是页面能适应手机和电脑等不同尺寸，不只是把字体缩小。截图或录屏能说明当时看到的画面，但不自动证明后端数据和权限也正确。

### 8.4 正式文档的类型和事实来源

Yuxi 的 `docs/` 按读者要完成的任务与需要了解的问题组织：

| 目录或材料 | 主要用途 |
|---|---|
| `intro/` | 按顺序教用户完成一个任务 |
| `advanced/` | 配置和运维参考 |
| `agents/` | Agent 配置及扩展方法 |
| `mechanisms/` | 原理、状态、权限、故障和源码定位 |
| `decisions/` | 非显然设计选择、备选方案与后果 |
| `postmortems/` | 事故经过、原因和改进 |
| changelog | 已发布的变化 |
| roadmap | 尚未完成的方向 |
| `docs/vibe/` | Git 忽略的本地临时计划 |

每个重要事实有一个主要说明位置（文档 Owner）；其他页面可以保留必要摘要和链接，不要维护多个各自独立、容易互相矛盾的完整副本。架构主链路归根 `ARCHITECTURE.md`，测试命令归测试规范，工程信任规则归对应专题。

源码、数据约束、Schema、Compose 和测试是核对当前可执行行为的重要依据；旧文档、外部 Wiki、历史 PR、AI 报告更适合作为线索。源码和测试也可能存在错误，因此应区分**项目承诺**、**代码实际行为**和**已做的验证**。

### 8.5 怎么写一篇可维护的技术文档

正式文档要先明确读者、目标、非目标和前置知识。**教程**按步骤让人完成任务；**参考文档**便于查参数和规则；机制文档解释组件、状态、权限和失败。有实质性混合时，本项目要求拆开。

调查一条真实链路时，可以从入口出发，搜索到 service / executor（真正执行操作的组件），再看 repository、持久化或事件发布，最后检查用户或模型看到什么；同时核对失败路径、权限、可选能力和测试。

项目的完整文档流程要求先规划章节，每节回答明确问题；按节完成事实与链接核对；先更新主要事实所在页面，再更新导航和引用。移动或拆分页面时，修复其他页面指向它的**入站链接**，不留两份各自维护的正文。小文案和机械链接清理可只查直接相关内容；文档改动提交前仍需项目要求的验证和独立 Review。非平凡的信息架构或长期约束变化要先建立 Git 跟踪的 proposed decision（提案决策记录）。

正式文档使用具体、可核实的现在时，写清执行者、条件、顺序、结果及失败后果；不确定时说明，未执行的验证标 `Not run`。决策原因放 decision，事故时间线放 postmortem；不把 PR 讨论和修改过程当成当前事实。已实施的 `implemented` 决策按现状描述，避免残留像未完成一样的提案待办。

不要手写容易漂移的完整 API、配置或文件清单，应链接当前源码或可生成的来源。`docs/` 站内用相对 Markdown 链接，站外公开源码用项目规定的 GitHub 链接；示例只用占位凭据和假 ID，不带真实账号、密钥、用户数据或本机绝对路径。

例如写“消息投递机制”时，先从事件路由定位 `accept_message`，再追到事务提交、调度、队列投递和最终状态；每跨过一个边界就记下输入、输出和失败路径。完成后把关键代码链接放在解释附近，让读者既能理解为什么，也能继续核对实现。

### 8.6 文档站构建不等于事实验证

新增正式站点页面时，项目要求在 `.vitepress/config.mts` 更新正确的导航位置；内部 Agent 指令、决策和事故复盘不会仅因放在 `docs/` 就自动进入用户导航。本站有 Agent 指令文件的字符预算，属于持续运行的自动护栏（standing-order guardrail）：超限先把背景和示例放到专题、压缩重复；确需提高要同步修改决策和检查，不能悄悄关闭检查。

文档 build（构建）能检查 Markdown、导航和链接等，但**不能证明文章中的业务解释正确**。应查相关源码和测试，再由审查者核对。遇到坏链接修链接、锚点或导航，不能仅通过扩大 `ignoreDeadLinks` 范围掩盖失败。

## 9. 协作、命令与阅读练习

### 9.1 Git、Diff、提交和审查

**Git** 记录项目文件的版本；**tracked** 文件在 Git 的版本管理范围内，**untracked** 文件尚未加入。**Diff** 是两个版本或工作区之间的差异；**commit** 是一次记录的变更；**PR（Pull Request）**是请求他人审查并合并变更的一种方式。

项目要求代码提交前由没有继承开发上下文的全新 Reviewer Agent 审查需求、差异、测试和规范，并修复实质问题。审查不仅检查“代码能跑”，还问方案是否必要、职责是否放对、有没有更简单的既有能力。测试通过能说明测试覆盖的行为，不自动说明设计是必要的。

该独立 Agent 审查方式是 **本项目的 AI 工作流程**。其他团队可能由人审查，或采用不同流程；可迁移的核心是让独立视角核对需求、代码、证据和风险。

项目要求中文 Conventional Commit：提交信息使用约定的类型前缀加简洁说明，例如假设的 `fix: 修正空列表提示`。PR 要说明受影响行为、归属、验证、风险和未验证范围。`git diff --check` 检查差异中的空白等问题；文件末尾保留一个换行，有助于工具处理。它不证明功能正确。

### 9.2 规范中的命令各是什么意思

下面把规范中常见的检查命令拆开解释。命令需要在对应工作目录运行；容器相关命令需要服务和依赖已就绪。完整要求见 [测试规范](../docs/develop-guides/testing-guidelines.md)。

| 命令或片段 | 目的与注意点 |
|---|---|
| `python3 scripts/ci/verify_engineering_contracts.py` | 运行项目的工程约定检查脚本。 |
| `python3 -m unittest scripts.ci.test_verify_engineering_contracts` | 测试上述检查脚本自身。 |
| `docker compose exec api uv run --no-sync --group test pytest test/unit -m "not slow"` | 在运行中的 `api` 容器里，通过 `uv` 运行不标记 slow 的后端单元测试。 |
| `(cd backend && uv run ruff check yuxi)` | 在 backend 目录运行 Ruff 静态检查。括号内先切换工作目录；Ruff 是 Python 检查工具。 |
| `(cd backend && uv run ruff format yuxi --check)` | 检查代码格式，`--check` 表示检查而非直接格式化。 |
| `(cd backend && uv run ruff check --select I yuxi)` | 检查导入语句排序。Ruff 属于后端 dev 依赖组，项目说明只装 test 组的 API 镜像不用于运行它。 |
| `docker compose exec frontend pnpm run lint:check` | 在 frontend 容器做只读静态检查。`lint:check` 是检查门槛；项目的 `lint` 允许自动修复，因此可能修改文件。 |
| `docker compose exec frontend pnpm run test:unit` | 在 frontend 容器运行前端单元测试。 |
| `docker compose exec frontend pnpm run build` | 在 frontend 容器构建前端，检查能否打包。 |
| `cd docs && pnpm run build` | 在 docs 目录构建文档站，用于检查正式文档站。 |
| `git diff --check` | 检查 Git 差异中的空白等补丁问题；不检查未跟踪文件的完整内容，也不验证业务行为。 |

根规范的最低测试表还规定：文档/导航变更检查相对链接与文档构建；公开行为变化要结合代码验证。后端和前端各自列有额外检查。实际修改时应按受影响范围阅读对应规范，不能只照抄这张学习表。

以 `docker compose exec api uv run --no-sync --group test pytest test/unit -m "not slow"` 为例，从左向右拆：`docker compose exec api` 在已经运行的 `api` 服务容器中执行后面的命令；`uv run` 使用项目 Python 环境启动命令；`--group test` 选择测试依赖组，`--no-sync` 不在这次运行前同步依赖；`pytest test/unit` 选择单元测试目录；`-m "not slow"` 只选择没有 `slow` 标记的测试。运行前需要容器和相应依赖已就绪。

### 9.3 三个练习：怎样把规范用起来

**练习一：空列表。** 请求还没回来时显示 loading；成功返回空列表显示 empty；请求失败显示 error。若把错误显示为空，用户会以为文件消失了。验证时分别模拟慢请求、空结果和错误，再检查真实页面。

**练习二：删除权限。** 普通用户看不到删除按钮仍可能直接调用接口。后端要结合当前身份、目标文件和操作检查权限；测试分别验证有权用户能删除、无权用户收到拒绝且文件仍存在。

**练习三：后台处理。** “已接收”说明输入已保存，解析或模型执行仍在后面。提交后到投递前可能中断，已经创建的 `pending` Run 由恢复扫描核对后补投；运行中的 worker 租约过期则记录失败和结果未知。沿 [接收服务](../backend/yuxi/modules/agents/services/inputs.py)、[调度服务](../backend/yuxi/modules/agents/services/scheduler.py)、[Run Repository](../backend/yuxi/modules/agents/repositories/runs.py) 各找出相应步骤。

自己练习时先画出调用顺序，再问每一步保存了什么、失败后用户看到什么、如何验证。

### 9.4 建议的继续阅读顺序

1. 先看 [README](../README.md) 和 [项目架构](../ARCHITECTURE.md)，认识主要服务。
2. 结合 [个人项目学习笔记](个人知识库与智能体项目学习笔记.md) 的 Docker 与对话部分，理解一个请求需要哪些组件。
3. 按“前端 → API → service → repository → worker → 结果”追一条具体操作；不理解时回本笔记查术语。
4. 阅读对应的 [Agent 运行时机制](../docs/mechanisms/agent-runtime.md) 或 [知识库机制](../docs/mechanisms/knowledge-base.md)，再看相关测试。
5. 最后再读 [工程测试规范](../docs/develop-guides/testing-guidelines.md) 和项目其他细则；不要把尚不熟悉的规则硬背下来。

| SaaS / Public API | 通过网络提供的软件服务 / 提供给外部调用者的公开接口；是否免费或兼容由具体产品决定。 |

| Token / secret / `.env` | 可证明身份或调用服务的凭据 / 秘密值 / 常用来保存本地环境配置的文件。模型的“token（文本单位）”是另一个含义。 |
| decision / postmortem | 设计决策记录 / 事故复盘。 |
| workflow / guardrail | 工作流程 / 用于限制错误、提供保护的规则或检查。 |
| SSE / 事件流 | 服务端通过持续 HTTP 连接推送事件的方式 / 随时间传输的一系列事件；断线恢复需要额外设计。 |
| 手动/自动验证 | 人实际操作检查 / 程序按脚本运行检查；两者都要说明具体覆盖范围。 |
