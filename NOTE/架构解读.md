## 第一章：鸟瞰——整个系统有哪些部分

> 本章按照 [ARCHITECTURE.md 的鸟瞰章节](../ARCHITECTURE.md#鸟瞰)逐段阅读。先建立地图，再到后面的章节追踪实际调用；这里先画出主要组成，具体操作再沿对应路径深入。

### 1.1 平台整体：网页、后端与知识能力

> 原文位置：[ARCHITECTURE.md 第 9 行](../ARCHITECTURE.md#L9)。


**原文**

> Yuxi 是一个面向 RAG、知识图谱和多智能体工作流的知识库平台。用户通过 Vue 前端管理智能体、知识库、模型、工具、Skills、MCP 与协作会话；前端通过 `/api` 调用 FastAPI；后端服务层协调 PostgreSQL、Redis、MinIO、Milvus、Neo4j、LangGraph 和沙盒。

**通俗理解**

用户在网页操作，网页把请求交给后端；后端根据需要组织智能体、模型、工具和各种存储服务。比如把论文上传到知识库，再问“作者用了什么实验方法”，当会话具备对应知识库的访问权限并使用检索工具时，系统可以检索论文相关内容，再让模型结合问题生成回答。

**业务名词**

| 名称 | 一句话理解 | 在本项目中的位置或用法 |
|---|---|---|
| 知识库 | 管理、处理和使用资料的业务功能 | 文档上传、解析、检索等由知识域负责 |
| RAG | 检索增强生成：检索资料并让模型结合检索内容回答 | 有权限且配置合适时，Agent 可以调用知识库检索工具 |
| 知识图谱 | 把实体及它们之间的关系组织成图 | 可从知识库中构建并查询实体关系，Neo4j 存储图谱部分 |
| Agent（智能体） | 结合模型、提示词、上下文和工具处理任务的程序 | 不仅能回复，也能在权限与配置允许时调用工具 |
| 协作会话 / 多智能体 | 多个相互关联但各有身份的会话协作 | 子会话可分工；并非每次提问都会启用 |
| Skill | 告诉 Agent 何时、怎样完成一类任务的能力包 | 可以含说明、参考文件、脚本及依赖声明 |
| MCP | 供 Agent 发现和调用工具服务的协议 | 内置知识库也通过 MCP 提供读取工具 |

**技术组件：各管什么**

| 名称 | 类别 | 作用，先理解到这一层即可 |
|---|---|---|
| Vue | 前端框架 | 组织浏览器中的页面、输入框和按钮 |
| FastAPI | Python Web 框架 | 定义 HTTP 接口，接收和返回请求 |
| `/api` | 接口地址前缀 | 例如 `/api/agent`；它不是独立应用名称 |
| PostgreSQL | 关系型数据库 | 保存用户、消息、任务状态、知识库元数据等持久业务事实 |
| Redis | 缓存和消息系统 | 本项目用于 ARQ 投递、短期事件、取消信号与缓存 |
| MinIO | 对象存储服务 | 保存知识库原文件、附件草稿等对象内容 |
| Milvus | 向量数据库 | 存储及检索向量数据等知识检索结构 |
| Neo4j | 图数据库 | 保存及查询知识图谱中的实体和关系 |
| LangGraph | Agent 流程框架 | 组织模型、工具和运行状态 |
| 沙盒 | 受限制的执行环境 | 按实际需要提供命令或文件操作环境，不是所有对话都使用 |

这些技术不互相等价。PostgreSQL 侧重业务记录，MinIO 偏向文件对象，Milvus 和 Neo4j 分别处理不同检索结构；拆分增加了系统组件和维护成本，换来不同类型数据各有合适的访问能力。这也意味着一次请求可能跨越多个服务，排查时需要确认每一步实际使用了哪种存储。

**看一条真实代码路径：网页怎样通过 `/api` 获取智能体列表**

前端在 [agent_api.js](../frontend/src/apis/agent_api.js#L26) 里定义了一个获取智能体列表的函数：

```js
getAgents: () => apiGet('/api/agent'),
```

`getAgents` 是函数名称；`apiGet` 表示发起查询请求；`/api/agent` 是请求的路径。这行代码只负责发请求，不在浏览器里直接查询数据库。

接下来的链路是：

1. 开发环境的 [vite.config.js](../frontend/vite.config.js#L91) 中，`server.proxy` 把 `/api` 请求转发给配置的后端地址；Compose 的 [frontend 服务](../docker-compose.yml#L271)设置为 `http://api:5050`。该服务名是容器网络内使用的地址，不必让用户在浏览器中输入。
2. [后端应用入口 main.py](../backend/yuxi/api/main.py#L108) 的 `app.include_router(..., prefix="/api")` 为业务路由加统一前缀。
3. [智能体管理路由](../backend/yuxi/api/routers/agents/management.py#L93) 的 `agent_router` 使用 `/agent` 前缀，`list_agents` 获取当前用户可见的智能体。

以上链路用于加载智能体列表，Vite 转发对应本项目开发配置；发送聊天消息的完整链路见[第 4 章](#智能体运行链路)。

**智能体如何组装？** 从 [ChatbotAgent 的 graph.py](../backend/yuxi/modules/agents/runtime/agent_backends/chatbot/graph.py) 找 `get_graph`：它准备模型、工具、提示词、中间件和检查点，再调用 `create_agent`。第一次阅读先找到这些词，不要求理解框架内部所有实现。

### 1.2 一条消息：接收、排队、运行与展示

> 原文位置：[ARCHITECTURE.md 第 11 行](../ARCHITECTURE.md#L11)。


**原文**

> 普通智能体消息先在 PostgreSQL Input 中保存原始内容，Receipt 保存幂等接收事实。调度器消费就绪输入时原子创建正式 Message、Turn 与首个 Run；steer 优先于 follow-up，运行中在安全边界接续当前 Turn。人工等待恢复沿用当前 Turn，产生下一段 Run。消费事务提交后，pending Run 通过 Redis/ARQ 交给独立 worker 执行。Redis Stream 保存短期增量，PostgreSQL 保存执行和业务终态，前端分别显示待处理队列和正式消息历史。

**通俗理解**

Yuxi 不把“请求已收到”“后台正在处理”“结果已经完成”混成一个状态。可以想成餐厅先记录顾客点单，再把订单交给厨房；厨房处理完成后，系统才记录最终出餐结果。真实代码比这个比喻复杂，尤其涉及用户身份、权限、附件与故障恢复。

```text
网页提交消息
  → 持久保存 Input 和 Receipt
  → 调度器挑选满足条件的输入
  → 在事务中创建正式 Message、Turn 和 Run
  → 事务提交后通过 ARQ 投递待执行 Run
  → worker 执行模型和工具
  → 短期过程事件与持久最终状态分别保存
  → 网页展示排队状态、过程与最终消息
```

**关键词不要混淆**

- **Input**：一次提交的原始输入；**Receipt**：接收回执，记录接收和幂等相关事实。幂等是为了让同一次请求重试时不会意外变成多份不同操作，具体约束取决于接口。
- **Message**：进入正式会话历史的消息；**Turn**：一轮工作的业务单位；**Run**：实际执行的一个阶段。同一 Turn 在等待人工回答或审批后，可能由新的 Run 接续。
- **调度器**：决定当前应该消费哪个输入。**follow-up** 是普通后续输入；**steer** 是希望改变正在进行的方向的输入。项目规定 steer 优先，并只在安全边界接管，具体队列规则见后续“智能体运行链路”。
- **事务**：一组数据库操作作为整体提交；**原子创建**指这组事实按其事务边界一起成功或失败。**pending** 是待执行状态，不等于任务已经完成。
- **worker**：后台执行程序；**ARQ**：这里用于把任务投递给 worker 的队列工具；**Redis Stream**：保存短期的运行事件。长期业务状态由 PostgreSQL 拥有，而不是把短期事件当唯一结果。

**为什么这样设计？** 如果浏览器刷新或网络中断，系统仍有持久输入与结果可供查询；如果一次任务需要等待人工操作，可以保留这轮任务和执行阶段的归属；多个输入同时等待时，调度器需要明确先后规则。“先提交再投递”让 worker 读取时能够找到已提交的 Run；如果提交后队列发布失败，恢复扫描会核对会话和 Turn 等归属，再补投符合条件、仍为 pending 的同一个 Run。已经执行失败的工作属于另一种情况，见[第 4 步](#第-4-步数据库提交后再交给后台队列)。

**用一次具体请求串起来。** 假设你在会话 `thread-1` 里发送“总结这篇论文”：系统先保存这次 Input 和接收回执；调度器领取后生成正式 Message、一个 Turn 和首个 Run。如果该 Run 运行到需要你审批的位置，审批后可用新的 Run 接续同一个 Turn。这样“用户这轮想完成的事”和“执行到了第几个阶段”有各自的身份，排查时可以分别查询。

**源码入口**

- [输入接收 inputs.py](../backend/yuxi/modules/agents/services/inputs.py)：看 `accept_message` 和 `accept_locked`，以及提交后调用调度的顺序。
- [调度器 scheduler.py](../backend/yuxi/modules/agents/services/scheduler.py)：看 `claim_next_input`、`dispatch_next_input`、`deliver` 与 `recover_pending_dispatches`；恢复扫描是进一步核对投递失败时行为的入口。
- [输入队列 repository](../backend/yuxi/modules/agents/repositories/input.py)：`ready_batch` 展示就绪输入如何选批。
- [worker 运行 runner.py](../backend/yuxi/modules/agents/services/runner.py)：从 `process_agent_run` 开始看运行入口与后续处理。

### 1.3 服务逐项解读：前端 `frontend`

> 原文位置：[ARCHITECTURE.md 第 15 行](../ARCHITECTURE.md#L15)。


**原文**：`frontend`：Vue 3 / Vite 前端，挂载 `frontend/src` 并热更新。

**它负责什么？** 为用户提供网页。Vue 是组织界面的框架，Vite 是开发服务器和构建工具。`frontend` 是 Compose 的服务名；对用户来说，浏览器访问本机端口即可看到网页。

**代码与配置**

- [Compose 的 frontend 服务](../docker-compose.yml)：找到 `frontend`，它选择 `docker/frontend.Dockerfile` 的 `development` 阶段，执行 `pnpm run server`。
- [frontend/package.json](../frontend/package.json)：`server` 脚本运行 `vite serve --host`。
- [前端入口 main.js](../frontend/src/app/main.js)：`createApp(App)` 创建 Vue 应用，装载路由与状态并 `mount('#app')`；[index.html](../frontend/index.html) 中定义了这个网页元素。
- [Vite 配置](../frontend/vite.config.js)：`server.proxy` 负责开发环境的 API 转发；`server.watch` 使用轮询来检查文件变化。

**为什么有“挂载”和“热更新”？** Compose 将宿主机 `./frontend/src` 绑定到容器 `/app/src`，容器能看到本机源码修改；Vite 发现变化后通常可热更新或必要时刷新页面。Vue 的 `app.mount` 是将界面装入网页元素，和 Docker 绑定目录是两种不同的“挂载”。热更新主要方便开发，不表示所有修改都不需要重启；依赖声明更改通常要重新安装依赖或构建镜像，生产方式也不同。

这条目录绑定可以在 [Compose 配置](../docker-compose.yml#L277)中直接看到：

```yaml
volumes:
  - ./frontend/src:/app/src
```

冒号左边 `./frontend/src` 是相对 Compose 文件所在目录的宿主机路径；右边 `/app/src` 是容器里的目标路径。开发时修改左边文件，容器能看到相应变化，再由 Vite 决定怎样通知浏览器。配置还分别挂载 `test`、`public`、`index.html` 和 `vite.config.js`；例如修改未挂载的依赖清单时，需要更新容器环境。

### 1.4 服务逐项解读：后端 `api`

> 原文位置：[ARCHITECTURE.md 第 16 行](../ARCHITECTURE.md#L16)。


**原文**：`api`：FastAPI API 服务，挂载 `backend/yuxi` 和测试目录；API 与 worker 的源码修改通过显式重启生效。

**它负责什么？** `api` 是接收网页或其他客户端 HTTP 请求的后端进程。用户访问接口时，它进行协议适配、身份检查等，并调用相应业务代码；长时间后台工作由 worker 等组件执行。

**为什么要显式重启？** 开发 Compose 让容器看到宿主机的后端源码，见 [api 服务配置](../docker-compose.yml) 的 `volumes`；文件更新后，已运行的 Python 进程仍持有之前导入的模块；因此文档要求修改后端源码后显式重启相应的 API 和 worker，让进程重新加载代码。

**源码入口**：[backend/yuxi/api/main.py](../backend/yuxi/api/main.py) 创建 FastAPI 并挂载路由；[routers 汇总](../backend/yuxi/api/routers/__init__.py) 可查看按业务注册的接口。

### 1.5 服务逐项解读：后台 `worker`

> 原文位置：[ARCHITECTURE.md 第 17 行](../ARCHITECTURE.md#L17)。


**原文**：`worker`：ARQ worker，执行已经派发的 AgentRun 与注册的后台作业，并周期触发用户自建 Agent 定时任务；三者分别使用 PostgreSQL 中的运行租约、任务租约和调度锁闭合并发与恢复。

**它负责什么？** worker 是独立的后台工作进程。它不等于网页 API：API 接收请求后，部分工作需要排队并交给 worker 执行，比如一次 Agent 运行、知识处理后台作业或定时任务。

**术语拆解**：AgentRun 是一次 Agent 执行段；后台作业是知识解析等独立任务；定时任务是在约定时间触发。**租约 lease** 是有期限的执行权声明，**调度锁** 用来协调并发调度，避免多个执行者无规则争抢；具体失败恢复还要看对应实现，不能理解为绝不重复或绝不失败。

**源码入口**：[Compose worker](../docker-compose.yml) 中的启动命令；[workers/main.py](../backend/yuxi/workers/main.py) 引入 `WorkerSettings` 并启动；[workers/settings.py](../backend/yuxi/workers/settings.py) 注册 `process_agent_run` 和 `process_background_job` 等任务。定时任务的启动与恢复装配还需继续看 [bootstrap/worker.py](../backend/yuxi/bootstrap/worker.py)。

### 1.6 服务逐项解读：`storage-init`

> 原文位置：[ARCHITECTURE.md 第 18 行](../ARCHITECTURE.md#L18)。


**原文**：`storage-init`：无网络的一次性进程，准备 API/worker/app-init 与 Milvus 挂载根的属主和模式，不递归修改已有文件；消费进程等待其成功退出。

**它负责什么？** 像开店前先整理好货架目录，让后续服务可以按预期访问它们需要的挂载目录。**属主**是文件系统中的所有者；**模式**控制读、写、进入等权限。它只处理列出的挂载根，不递归改写里面已有用户文件。

**为什么单独做？** 如果目录权限不匹配，后续进程可能无法读写数据；把准备工作单独执行并让依赖方等待成功，可以尽早暴露问题。它不需要网络，也不是一直运行的 Web 服务。

**源码入口**：[Compose storage-init](../docker-compose.yml) 配置 `network_mode: none` 和依赖；[storage-init.sh](../docker/storage-init.sh) 可直接看到对根目录执行的 `chown` 和 `chmod`。这里讨论项目脚本，不建议读者自行对现有数据目录运行权限修改。

### 1.7 服务逐项解读：`app-init`

> 原文位置：[ARCHITECTURE.md 第 19 行](../ARCHITECTURE.md#L19)。


**原文**：`app-init`：普通用户运行的部署任务，在 PostgreSQL advisory lock 内先建立或校验当前 Schema，再同步系统配置定义、内置供应商、Agent、MCP 与 Skill 来源文件。API 与 worker 等待全部成功。空库基线为 business 1、knowledge 2，直接包含个人 MCP 授权表、128 位用户归属字段及当前约束。当前版本跳过结构初始化，其他版本明确拒绝；历史部署的结构调整由部署侧显式完成；知识域 v1 路径目录通过离线审计/转换入口升级 v2，运行进程不自动迁移。共享同步失败保留已提交内容，修正后幂等重跑。

**它负责什么？** 这也是部署准备任务，不是普通聊天接口，由普通用户身份运行；API 和 worker 等它成功之后再启动。它为应用准备数据库结构及代码拥有的初始共享配置。**Schema** 指表、列和约束等数据库结构；`business 1` 与 `knowledge 2` 是这个版本分别记录的结构版本，不是数据库里只有一张或两张表。空库基线已包含个人 MCP 授权表、128 位用户归属字段及当前约束；“128 位”描述字段所能表示的信息位数，不是允许 128 个用户。

**为什么有 advisory lock（数据库咨询锁）？** 如果多个初始化进程同时尝试建表或同步共享配置，可能发生竞争。数据库锁用于让遵循同一锁约定的初始化流程串行。这样多个遵循该约定的初始化进程就不会同时进行这段工作。

**为什么不是自动升级一切？** 源码 [migrations/main.py](../backend/yuxi/migrations/main.py) 的 `initialize_schema` 区分空库、当前版本和不支持的已有版本；不兼容版本明确失败，而不是把旧库悄悄当成可用。共享初始化包含多阶段提交，失败可能留下已提交内容；[bootstrap/app.py](../backend/yuxi/bootstrap/app.py) 的 `main` 描述修正后可幂等重跑。**幂等**是按约定重复执行不会意外产生重复效果；遇到不支持的旧版本时，需要先按项目要求处理升级。

**源码入口**：[Compose app-init 与依赖](../docker-compose.yml)、[初始化入口](../backend/yuxi/bootstrap/app.py)、[数据库结构初始化](../backend/yuxi/migrations/main.py)、[版本常量](../backend/yuxi/infrastructure/postgres/schema.py)。文档还说明旧知识域 v1 路径目录需离线审计或转换，不能据此推断本机已发生升级。

### 1.8 两种执行环境：Cube 与 `sandbox-runner`

> 原文位置：[ARCHITECTURE.md 第 20 行](../ARCHITECTURE.md#L20)、[ARCHITECTURE.md 第 21 行](../ARCHITECTURE.md#L21)。


**原文**：Cube Linux/KVM 执行节点：每个用户拥有一个持久普通账号 VM，Workspace 与授权 Skills 共享宿主文件。

**通俗理解**：Cube 是项目支持的一种沙盒后端。VM 是虚拟机，可以理解成独立运行的虚拟电脑；Linux/KVM 是这条部署方式依赖的虚拟化环境。按照文档，用户拥有持久的普通账号 VM，并与宿主文件共享工作区和获授权的 Skill；需要按它的部署要求准备节点。

**原文**：`sandbox-runner`：选择 container 后端时由该独立进程持有 Docker socket，为每个 Run 懒创建临时容器并执行命令；API/worker 只调用认证 HTTP。挂载、镜像和资源限制由 runner 拥有，Run 归属与清理责任仍由 PostgreSQL 拥有。

**通俗理解**：另一个选择是容器后端。独立 runner 持有 Docker socket（与 Docker 引擎通信的接口），真正需要执行时才为该 Run 创建临时容器；API 与 worker 通过受认证保护的 HTTP 调用 runner，而不是都直接持有 socket。

**为什么把权限分开？** Docker socket 能控制容器，集中在专用进程有助于缩小哪些程序直接持有该能力。镜像、挂载和资源限制由 runner 执行；“这个 Run 属于谁、何时需要清理”等持久事实仍由 PostgreSQL 保存。临时容器不等于持久 Workspace：运行结束后容器可以销毁，工作文件按项目工作区设计保留。

**源码入口**：[container profile 与 sandbox-runner](../docker-compose.yml)、[容器后端说明](../docs/advanced/container-sandbox.md)、[Cube 运行适配](../backend/yuxi/modules/agents/runtime/sandbox/cube.py)。两种后端不能当成同时必须启动的服务；具体当前实例是否能执行命令需要实际验证。

### 1.9 服务逐项解读：`postgres`

> 原文位置：[ARCHITECTURE.md 第 22 行](../ARCHITECTURE.md#L22)。


**原文**：`postgres`：业务数据、知识库元数据、持久 Input 队列、Turn/Run 与 LangGraph checkpoint。

**通俗理解**：PostgreSQL 是项目的关系型数据库。**元数据**是描述数据的信息，例如一个文件的名称、所属知识库和处理状态；文件原始字节不必全部塞进同一张数据库表。它还保存用户输入、当前运行和结果等长期需要核对的事实。

**checkpoint** 是执行过程的状态检查点，为特定状态读取和恢复提供依据；它不等于 Redis 中临时实时事件，也不等于模型每次回复的最终业务结果。为什么分开？不同数据寿命、读取用途和一致性要求不同；核心结果不能只依靠可能过期的短期事件。

**源码入口**：[Compose postgres](../docker-compose.yml)；[输入与回执模型](../backend/yuxi/modules/agents/models/inputs.py)；[Run 模型](../backend/yuxi/modules/agents/models/runs.py)；[LangGraph PostgreSQL checkpointer](../backend/yuxi/infrastructure/postgres/checkpointer.py)。这些文件适合等理解一轮对话再逐项阅读。

### 1.10 服务逐项解读：`redis`

> 原文位置：[ARCHITECTURE.md 第 23 行](../ARCHITECTURE.md#L23)。


**原文**：`redis`：ARQ 投递、运行事件、取消信号以及跨进程配置和模型缓存。

**通俗理解**：Redis 在这里更像一个供不同进程快速交换信息的地方：ARQ 使用它传递待执行工作，运行过程产生的事件可以写入 Redis Stream，取消信号和部分缓存也经过它。

**为什么需要它？** API 和 worker 是不同进程，不能只靠一个 Python 变量互相通知；同时，模型输出可能一段段到来，前端需要看到过程。项目用 Redis 承担这些短期协作职责，同时把最终业务事实交给 PostgreSQL。页面重连时，需要结合短期事件与 PostgreSQL 中的持久记录恢复视图。

**源码入口**：[Compose redis](../docker-compose.yml)、[Agent 任务投递 transport.py](../backend/yuxi/modules/agents/services/transport.py)、[事件写入 event_writer.py](../backend/yuxi/modules/agents/services/event_writer.py)。

### 1.11 服务逐项解读：`minio`

> 原文位置：[ARCHITECTURE.md 第 24 行](../ARCHITECTURE.md#L24)。


**原文**：`minio`：附件草稿内容、知识库原始文件和其他对象数据；正式 Agent 附件归 Workdir，附件事实归 PostgreSQL。

**通俗理解**：MinIO 提供对象存储，可以先把它理解为专门存放文件内容的服务。用户上传但还没正式提交的附件草稿、知识库原文件等可放在这里。按架构文档，正式 Agent 附件内容归 Workdir（工作目录），而“附件属于谁、状态是什么”等业务记录由 PostgreSQL 管理。

### 1.15 知识库 MCP：同一服务中的一条工具接口

> 原文位置：[ARCHITECTURE.md 第 29 行](../ARCHITECTURE.md#L29)。


**原文概要**：API 在 `/api/mcp` 提供只读知识库 MCP，与 HTTP API 共用进程和端口；知识域负责协议、内部认证、连接定义、产品读取及引用转换，通用 MCP 负责工具发现和调用策略。外部客户端使用 API Key，内部 Agent 按用户及会话选择使用五分钟短期委托凭据。知识库每次调用复核用户权限与会话选择的交集；`knowledge-base` Skill 通过 `mcp_dependencies` 声明知识服务依赖；选择器及引用读取也通过 SDK 访问 MCP；关闭 Knowledge 后接口和能力明确不可用。

**先解释词**：

- **MCP server**：按 MCP 协议提供工具的一方；**client**：发现并调用工具的一方。
- **只读**：此知识库 MCP 提供读取和查询用途，不代表项目整体不支持上传或修改。
- **SDK**：软件开发工具包，封装协议连接与调用；**Token / API Key** 是凭据，不应写入笔记或截图。
- **委托凭据**：内部调用为代表实际运行用户而使用的短期凭据；五分钟是本版本配置，而非 MCP 标准。
- **权限交集**：用户本来有权读取的范围，与当前会话选中的范围共同限定这次能访问什么。会话多选一个无权访问的知识库，不会自动获得权限。
- **mcp_dependencies**：Skill 声明需要哪些 MCP 服务；声明依赖也不能替用户绕过授权。

**简化数据流**：

```text
Agent 激活知识库 Skill
    → 通用 MCP 客户端发现 knowledge 服务的工具
    → 本次调用附带代表运行用户和会话选择的短期凭据
    → /api/mcp 中知识域验证身份及可见范围
    → 知识域实际执行查询并返回结果和可引用信息
```

架构中“选择器与引用读取也通过 SDK 调用 MCP”意味着这条读取能力不只给模型使用；知识库引用保留文件身份及行范围，方便追溯。关闭 Knowledge 时不再装配相应路由与 manager；代码保留内置身份，调用方能识别不可用，不应该把停用表现为凭空有结果。

**为什么不让模型直接读取所有库？** 模型只负责提出工具调用，真正的知识域在执行时重新检查身份、所选范围和权限。能力发现、工具可见与最终数据授权是不同边界。

**源码入口**：[API 应用挂载](../backend/yuxi/api/main.py) 条件装配知识 MCP；[MCP 服务](../backend/yuxi/modules/knowledge/mcp/server.py) 中 `KnowledgeMCP` 和工具处理；[知识委托凭据](../backend/yuxi/modules/knowledge/mcp/auth.py) 中 `KNOWLEDGE_DELEGATION_SECONDS = 300`；[内置 Skill 声明](../backend/yuxi/modules/extensions/skills/builtin/knowledge-base/SKILL.md)；[客户端与选择器](../backend/yuxi/modules/knowledge/mcp/client.py)；[引用转换](../backend/yuxi/modules/knowledge/mcp/references.py)。完整边界见 [知识库机制](../docs/mechanisms/knowledge-base.md)。

### 1.16 企业认证：OIDC 不是项目自带账号中心

> 原文位置：[ARCHITECTURE.md 第 31 行](../ARCHITECTURE.md#L31)。


**原文**：企业认证中心由部署方现有的 OIDC 服务提供；Yuxi 仅消费标准 OIDC/MCP 协议，不保存 Keycloak 部署模板或运行认证数据库。

**通俗理解**：OIDC（OpenID Connect）是一种基于身份提供方的登录协议。企业如果已有统一登录系统，可以按部署要求配置 Yuxi 作为客户端使用；企业认证中心由部署者自己提供。Keycloak 是一种可以充当身份服务的软件，这里文档说当前仓库不提供其部署模板或认证数据库，并不是说 Yuxi 完全没有自己的本地用户和权限数据。

**为什么区分？** 项目消费外部身份协议，与它自己负责提供并维护企业认证服务器，是两种不同职责。对接时需要配置认证地址、回调和用户映射。MCP 资源授权解决的是访问外部工具的问题，与用户登录平台的流程分别配置，详见项目机制说明。

**源码入口**：[OIDC 客户端](../backend/yuxi/infrastructure/oidc/client.py)、[OIDC 身份用例](../backend/yuxi/modules/identity/services/oidc.py)、[第三方认证说明](../docs/advanced/third-party-auth.md)。这里未对接真实企业认证服务。

## 二、后端代码地图：如何从代码中找到职责

这一章对照原文 [“后端代码地图”](../ARCHITECTURE.md#后端代码地图)。它不像聊天页面那样只讲一条操作，而是一张“代码放在哪里”的地图。第一次读时先记住：**业务逻辑放在按业务划分的模块里，HTTP 和后台进程是不同的入口，连接数据库等通用技术能力由基础设施提供。** 各段列举的是本项目的设计，具体行为仍以源码和测试为准。

### 2.1 后端的总目录、上传与文件边界

> 原文位置：[ARCHITECTURE.md 第 35 行](../ARCHITECTURE.md#L35)。


**原文要点：**`backend/yuxi` 是 Python 包；`api` 和 `workers` 是进程适配层，`modules` 管业务，`infrastructure` 管技术连接，`bootstrap` 管启动装配，`migrations` 管数据库结构修改。上传对象在 API 边界转换，文件边界负责限量与原子落盘。

#### 整体在说什么？

把后端想成一个处理用户任务的工厂：

```text
浏览器 → api：接收网络请求                 ┐
                                           ├→ modules：决定业务怎样完成
后台任务 → workers：接收已登记的任务       ┘
                         ↓
           infrastructure：连接数据库、存储、解析程序等
```

这张图展示职责归属：网页请求从 API 进入，后台任务从 worker 进入，两者可以调用同一个业务模块。

| 原文中的词 | 通俗解释 | 主要入口 |
|---|---|---|
| Python 包 | Python 代码组织和导入的单位；Yuxi 的后端主要代码在 `backend/yuxi` | [项目配置 pyproject.toml](../backend/pyproject.toml) |
| API 适配层 | 把 HTTP 请求转换成程序可处理的数据，再把结果变成 HTTP 响应 | [api/main.py](../backend/yuxi/api/main.py)、[api/routers](../backend/yuxi/api/routers/) |
| Worker 适配层 | 后台进程接收任务并调用对应的业务执行逻辑 | [workers/main.py](../backend/yuxi/workers/main.py) |
| 业务域与用例 | 把知识库、用户、智能体等业务按职责组织；用例表示“完成一件具体业务事” | [modules](../backend/yuxi/modules/) |
| infrastructure | 对 PostgreSQL、Redis、对象存储、文档解析等技术设施的封装 | [infrastructure](../backend/yuxi/infrastructure/) |
| bootstrap | 在进程启动时准备依赖、初始化组件并安排关闭 | [bootstrap](../backend/yuxi/bootstrap/) |
| migrations / Schema | 数据库结构变更代码 / 数据表、字段、约束等结构 | [migrations](../backend/yuxi/migrations/) |

**为什么分开？** 假设以后不仅网页要提交工作，后台定时任务也要做同样的事。如果业务规则只写在网页路由里，定时任务很难复用；将业务放在 `modules`，不同入口才有机会使用同一套规则。阅读新功能时，可以先找到入口，再跟进被调用的业务服务。

#### 上传文件时，为什么要区分网络对象和文件内容？

用户在浏览器上传文件时，FastAPI 用 `UploadFile` 表示一次 HTTP 上传。它属于这次请求的处理过程，不适合当成长期保存的业务数据。Yuxi 在 API 层把它转换成业务服务能使用的字节或文件流；服务消费这些输入，而不把 HTTP 上传对象当成持久业务对象。工作区文件边界负责限制文件大小，并按需采用**原子落盘**：让外部观察尽量只看到完整结果，不把尚未写完的目标文件当成已经完成的文件。

**为什么？** 网络请求有生命周期；请求结束后再依赖其中的上传对象，资源可能已经关闭。把 HTTP 对象限制在入口，也使业务服务不必依赖具体网页框架。写入边界还负责处理文件落盘和临时文件清理。

**去哪里看代码？**

- [api/uploads.py](../backend/yuxi/api/uploads.py)：从 `read_upload_with_limit` 和 `prepare_upload_files` 看文件大小检查、字节和流的处理。
- [工作区文件服务](../backend/yuxi/modules/workspace/services/files.py)：看工作区文件操作的入口；实际路径与权限边界还需沿其调用继续追。
- [共享文件契约](../backend/yuxi/shared/files.py)：看与某一种网页上传对象无关的文件输入、结果和通用处理。

### 2.2 四类启动装配：网页和后台程序如何开始工作

> 原文位置：[ARCHITECTURE.md 第 42 行](../ARCHITECTURE.md#L42)。


**原文要点：**`bootstrap/app.py` 是 `app-init` 入口，调用空库初始化与共享内容同步；`migrations/schema.py` 负责 DDL；`infrastructure/postgres/schema.py` 提供运行进程只读版本检查。

**通俗解释：**第一次部署一个空数据库时，系统需要先建立表、准备内置配置。`app-init` 是做这些准备的一次性初始化任务；API 和 worker 在启动时检查自己使用的数据库结构是否符合预期。**DDL**（数据定义语言）是创建或修改数据库结构的一类操作，例如建表、增加约束。

**代码入口：**[bootstrap/app.py](../backend/yuxi/bootstrap/app.py) 的 `main`；[migrations/main.py](../backend/yuxi/migrations/main.py) 的 `initialize_schema`；[migrations/schema.py](../backend/yuxi/migrations/schema.py)；[只读版本检查](../backend/yuxi/infrastructure/postgres/schema.py)。

### 2.4 业务模块：各自解决什么业务问题

> 原文位置：[ARCHITECTURE.md 第 48 行](../ARCHITECTURE.md#L48)、[ARCHITECTURE.md 第 49 行](../ARCHITECTURE.md#L49)、[ARCHITECTURE.md 第 50 行](../ARCHITECTURE.md#L50)、[ARCHITECTURE.md 第 51 行](../ARCHITECTURE.md#L51)、[ARCHITECTURE.md 第 52 行](../ARCHITECTURE.md#L52)。


#### （1）`modules/agents`：智能体任务怎样被接收、执行和结束

> 原文位置：[ARCHITECTURE.md 第 48 行](../ARCHITECTURE.md#L48)。


**原文要点：**Agent 模块管理 Input、消息、Turn/Run、调度、租约、运行状态和执行图；service 编排，repository 查询保存，model 描述数据；runtime 管具体执行、沙盒和中间件。知识库可见范围由 knowledge 业务负责。

**通俗解释：**用户发来一句话，系统不仅要问模型，还要记录是谁发的、现在执行到哪一步、最终答案属于哪次执行。这里先把 **Thread** 看作一个对话，**Input** 看作一次用户提交，**Turn** 看作一轮工作，**Run** 看作一段执行；项目实际关系比这个简化说法更细，后面的运行链路章节会展开。

- `services` 像业务流程负责人，协调不同步骤。
- `repositories` 专门提供数据访问；`models` 用 Python 类描述持久数据。
- Agent runtime 是模型、工具和规则真正组合运行的部分。
- middleware（中间件）是执行过程中的一层处理规则，例如围绕模型或工具调用做权限检查、审批或记录。

**为什么要规定锁顺序？** `run_lifecycle.py` 对 Thread→Turn→Input→Run 的锁序作约束。数据库锁可以避免多个任务同时修改同一事实时发生冲突；统一拿锁顺序能降低互相等待的风险，但不是凭一句规定就能证明所有死锁已消除。`steer` 是运行中的转引导输入，项目在规定的安全时机判定能否接续；不同事务由具体用例负责，不把所有事务都归同一函数。

**代码入口：**[输入接收 inputs.py](../backend/yuxi/modules/agents/services/inputs.py) 的 `accept_message`；[调度 scheduler.py](../backend/yuxi/modules/agents/services/scheduler.py) 的 `dispatch_next_input`；[run_lifecycle.py](../backend/yuxi/modules/agents/services/run_lifecycle.py) 的 `lock_run_lifecycle`；[ChatbotAgent 执行图](../backend/yuxi/modules/agents/runtime/agent_backends/chatbot/graph.py) 的 `get_graph`；[知识库访问判断](../backend/yuxi/modules/knowledge/services/access.py)。

#### （2）`modules/knowledge` 与 `modules/documents`：文档如何进入知识库

> 原文位置：[ARCHITECTURE.md 第 49 行](../ARCHITECTURE.md#L49)。


**原文要点：**knowledge 管知识库、上传导入、分块、检索、图谱与评估；documents 和 document_parsing 负责文档解析与产物；后台 worker 处理已登记工作。

**业务例子：**你上传一份 PDF，系统需要先接收并安全暂存原件，再登记文件和需要执行的工作，之后由后台处理。哈希是从文件内容计算的摘要，可用于识别内容；暂存不应被误解为“已经完成索引”。文本解析、分块和向量索引也不是同一件事。

```text
上传 / URL / 工作区来源
    ↓
读取、计算摘要并暂存原件
    ↓
登记目录、文件、接收回执及作业 → 事务提交
    ↓
后台 worker 处理解析、索引等作业
```

这是定位职责的概念图，不表示三种来源所有步骤完全相同。项目让目录、唯一名称、文件、幂等回执和作业在相关导入事务中登记，再投递后台工作：先留下可追踪的事实，能减少“后台开始了，但数据库还看不到文件”的问题；投递失败仍需要恢复机制。

图谱构建也有单独的准入、任务登记和执行责任：提交服务负责检查是否允许并登记 Job，worker 消费具体 action，图谱执行器负责具体配置与投影锁。**投影**在这里可理解为根据业务事实生成的图谱等外部数据视图，相关锁用于协调并发更改，不代表所有外部存储天然组成同一个数据库事务。**executor（执行器）**是实际完成某类操作的组件；本地文件读取、目录操作不必为了简单查询而加载完整索引执行器，解析或检索时才需要对应执行能力。

`modules/documents` 负责组织解析选项与输入，并把结果发布到调用方指定位置；`infrastructure/document_parsing` 更专注底层格式解析和本地 Markdown 目录。OCR 是从图片中识别文字的处理方式。分开这两层，业务用例和某个具体解析引擎之间就不必完全绑在一起。

**代码入口：**[暂存原件 uploads.py](../backend/yuxi/modules/knowledge/services/uploads.py) 的 `stage_document`；[导入 imports.py](../backend/yuxi/modules/knowledge/services/imports.py) 的 `register_import`；[图谱任务 graph_build.py](../backend/yuxi/modules/knowledge/services/graph_build.py) 的 `start_graph_build`；[文档解析 service](../backend/yuxi/modules/documents/service.py) 的 `parse`；[底层 parser](../backend/yuxi/infrastructure/document_parsing/parser.py)、[产物处理](../backend/yuxi/infrastructure/document_parsing/artifacts.py) 和 [OCR 引擎目录](../backend/yuxi/infrastructure/document_parsing/engines/)。

### 2.5 MCP：为什么一个外部工具还要管这么多身份和状态

> 原文位置：[ARCHITECTURE.md 第 54 行](../ARCHITECTURE.md#L54)。


**原文要点：**MCP 模块维护远程服务器、个人 OAuth 连接和加密凭据；授权事务绑定可信服务器、用户、浏览器与配置修订；数据库锁与连接世代处理并发和过期回调；每次 Run 按身份发现并检查可用工具，之后出站调用还要复查权限与配置。

先解释词汇：

- **MCP**：连接工具服务的一种协议。服务端可以告诉智能体有哪些工具、如何调用；这里既有服务器配置，也有每位用户的个人连接。
- **OAuth**：让用户把受限资源访问权限授予应用的一种授权流程。MCP 个人授权与用户登录 Yuxi 是两件不同的事。
- **信任根**：管理员明确指定应信任的授权服务器，而不是让不可信输入任意决定把用户送到哪里。
- **回调**：用户在授权页面完成操作后，浏览器返回应用的步骤。
- **修订/世代**：表示配置或连接的版本。旧版本请求晚到时，可以据此判断它是否仍然有效。
- **行锁**：数据库在处理某条记录时，对并发修改进行协调；这里用于处理令牌刷新和断开可能同时发生的情况。
- **Context**：当前一次 Run 使用的运行上下文，包含身份、配置与已装配资源等。它不是用户能随意伪造可信身份的地方。

回调返回的结果先暂存，之后由当前登录的 JWT 用户确认归属，才发布成可使用的连接。JWT 是应用用于识别登录会话的一种令牌；它与 MCP 资源服务使用的访问凭据是不同的东西。

**为什么这么复杂？** 假设用户点击连接后又立刻断开，但之前的授权页面很久以后才返回。如果系统只看到“授权成功”就保存连接，旧回调可能把用户刚刚断开的连接重新打开。绑定用户和配置修订、检查连接世代，可以防止旧事务无条件覆盖新状态。

对已授权工具，系统按当前运行的可信用户解析是否可用。当前 Run 内按需发现并复用目录，下一次 Run 可以重新发现；实际出站时还复查用户、服务配置、工具开关和连接状态。未连接外部 MCP 时普通聊天仍可继续，但依赖它的工具不可用。**“配置了服务”“已连接”“本轮能调用”是不同层面的事实。**

**代码入口：**[MCP service](../backend/yuxi/modules/extensions/mcp/service.py) 的 `resolve_runtime_mcp_tools`；[OAuth service](../backend/yuxi/modules/extensions/mcp/oauth_service.py) 的 `MCPOAuthService`；[个人 MCP 运行适配](../backend/yuxi/modules/extensions/mcp/oauth_runtime.py) 的 `PersonalMCPAuth`；深入说明见 [MCP 授权与运行身份](../docs/mechanisms/mcp.md)。

### 2.6 搜索与网页抓取：有工具名称不等于已经能用

> 原文位置：[ARCHITECTURE.md 第 56 行](../ARCHITECTURE.md#L56)。


**原文要点：**`modules/extensions/web` 管搜索、抓取和供应商适配；工具与管理员测试复用同一服务，调用时读取当前有效配置；未配置能力不进入当前运行的工具集合，凭据通过 system 的持久设置与脱敏边界管理。

### 2.7 Skills：多人编辑和运行时副本怎样保持一致

> 原文位置：[ARCHITECTURE.md 第 58 行](../ARCHITECTURE.md#L58)。


**原文要点：**Skills 分共享索引、个人来源、安装草稿、文件编辑和投影；共享编辑使用修订值拒绝过期保存；读取、运行快照和投影复制在锁下协作；个人 Skill 在用户工作空间边界访问。

**通俗解释：**Skill 可以是一份说明文件及其相关资源。共享 Skill 有权限范围，个人 Skill 属于个人工作空间。**草稿**是尚未正式确认的安装内容；**投影**可先理解为系统根据授权，为某个运行环境准备的一份可访问视图或副本。

**为什么需要修订值？** 假设甲和乙同时打开一份说明：甲先保存新版本，乙仍拿旧版本覆盖保存，就可能丢掉甲的修改。保存时比较文件修订值，可拒绝已经过期的提交，让乙先重新读取。**锁顺序**则用于协调权限变化、共享 Skill 和用户投影之间的并发操作：本项目规定授权变更先获取共享 Skill 行锁，再获取用户投影锁，提交并刷新投影。如果一条操作先锁共享 Skill、再锁用户投影，另一条却反过来锁，双方就可能互相等待；统一锁顺序是为了避免这类死锁。

**代码怎样防止覆盖？** [edit.py](../backend/yuxi/modules/extensions/skills/edit.py#L36) 的 `edit_shared_skill_file` 接收客户端读到的 `expected_revision`，并传给统一的内容提交入口：

```python
expected_file=(relative_path, expected_revision),
changes=[{"action": "write", "path": relative_path, "content": content}],
```

这里把“要写哪个文件、读取时看到的版本、要写入什么”一起交给 `commit_skill_content` 检查。若乙的版本已落后，保存会被拒绝，乙需要重新读取后处理冲突；修订值解决的是覆盖检查，行锁和投影锁负责协调并发修改与运行副本。

**代码入口：**[skills/edit.py](../backend/yuxi/modules/extensions/skills/edit.py) 的 `edit_shared_skill_file`；[skills/projection.py](../backend/yuxi/modules/extensions/skills/projection.py) 的 `refresh_user_skill_projection_async`；[skills/personal.py](../backend/yuxi/modules/extensions/skills/personal.py)；[Skills 管理](../docs/agents/skills-management.md)。

### 2.8 共享技术边界：错误如何跨越模块

> 原文位置：[ARCHITECTURE.md 第 62 行](../ARCHITECTURE.md#L62)。


**原文要点：**业务使用 `shared/errors.py` 的领域错误，HTTP API 在自己的边界把这些错误转换成状态码与响应；定时执行、文件预览、模型工具可直接按领域错误处理，不需要业务逻辑到处抛 HTTPException。

**通俗解释：** 领域错误是贴近业务含义的错误，比如“没有权限”“资源不存在”“当前状态不允许这个操作”。同一个业务逻辑既可能被网页请求使用，也可能被后台任务使用，因此内部表达“无权访问”，比直接写死“网页接口返回某个 HTTP 状态”更容易复用。到了 API 边界，再映射为 HTTP 响应。

**对照一条实际映射。** [shared/errors.py](../backend/yuxi/shared/errors.py) 定义 `PermissionDeniedError` 表达“当前身份无权操作”；[api/errors.py](../backend/yuxi/api/errors.py) 将它映射为 `403`，并由 `domain_error_handler` 生成响应。`ResourceNotFoundError` 映射为 `404`，`StateConflictError` 映射为 `409`。

这样同一业务错误在后台任务中仍能作为 Python 异常处理，到了网页接口边界才转换为 HTTP 状态。阅读时可以先找错误在哪里抛出，再找对应入口如何处理它，理解用户最终看到了什么。

### 2.10 三种后台工作：共享队列不等于共享同一种状态

> 原文位置：[ARCHITECTURE.md 第 68 行](../ARCHITECTURE.md#L68)、[ARCHITECTURE.md 第 70 行](../ARCHITECTURE.md#L70)、[ARCHITECTURE.md 第 71 行](../ARCHITECTURE.md#L71)、[ARCHITECTURE.md 第 72 行](../ARCHITECTURE.md#L72)。


**原文要点：**Agent 生命周期、用户定时 Agent、知识库后台作业三种机制共享 PostgreSQL 记录和 Redis/ARQ 投递方式，但领域状态不同，不应合并成一个状态模型。

#### （1）Agent 生命周期

> 原文位置：[ARCHITECTURE.md 第 70 行](../ARCHITECTURE.md#L70)。


Thread 是长期对话；Input 是持久接收的输入；Turn 是一轮工作；Run/Attempt 是执行段与尝试。某个运行可能等待用户审批或回答；执行树（execution tree）表示主任务及协作执行之间的关联。项目要求等待、输出和执行身份有明确归属，避免把别的一次运行的结果当成本次答案。

**代码入口：**[输入服务](../backend/yuxi/modules/agents/services/inputs.py)、[调度器](../backend/yuxi/modules/agents/services/scheduler.py)、[运行生命周期](../backend/yuxi/modules/agents/services/run_lifecycle.py)。这些词后续在“智能体运行链路”中会结合一步步的操作继续解释。

#### （2）用户定时 Agent

> 原文位置：[ARCHITECTURE.md 第 71 行](../ARCHITECTURE.md#L71)。


定时定义是“按什么规则做什么”，occurrence 是“一次具体触发”。worker 检查到期任务后，复用已有会话、输入和运行用例；一次触发保留来源关联，便于回查。它不能简单等同于长期定时设置本身。

**代码入口：**[定时模型](../backend/yuxi/modules/schedules/models.py) 的 `ScheduledAgentJob` 和 `ScheduledAgentRun`；[定时服务](../backend/yuxi/modules/schedules/service.py) 的 `claim_and_dispatch_due_jobs`。

#### （3）后台作业：解析、评估与构图

> 原文位置：[ARCHITECTURE.md 第 72 行](../ARCHITECTURE.md#L72)。


作业登记时记录 `job_type + handler_version + payload`：分别说明“工作是什么类型”“用哪个版本的处理方式”和“执行所需的参数”。事务提交后由 dispatch 投递，worker 根据 registry 找到 **Handler（具体处理程序）**并领取执行。惰性加载是在确实需要某种处理程序时才加载它，从而减少未使用的处理程序带来的启动加载开销。

数据库中的 BackgroundJob 行记录任务归属和状态，owner、heartbeat、lease 使执行责任可观察。知识库文件的处理中状态绑定作业尝试；失败时，领域失败处理与作业终态在相应事务中协调，避免“作业失败但文件永远显示处理中”。待投递的 PostgreSQL 记录可以由启动和周期发布器补发；这与无条件自动重复执行一个已经失败的业务操作不同。

`JobTracker` 内部读取持久记录，HTTP 对外输出只允许的字段；列表不默认生成完整结果详情。进度和最终状态由执行者上报，业务失败判定由相应领域负责；取消先记录请求，再由执行者在安全检查点响应。该项目的后台作业仅向管理员开放。共享 ARQ worker 的执行槽由 Compose 配置，当前代码限制后台作业的 PostgreSQL 同时领取上限为 4，目的是避免挤占 AgentRun 的执行容量；实际是否有剩余执行槽还取决于 ARQ worker 的总槽位设置。

**代码入口：**[作业登记与投递](../backend/yuxi/modules/background_jobs/dispatch.py) 的 `register_job_in_session`、`publish_job`；[作业注册表](../backend/yuxi/modules/background_jobs/registry.py) 的 `JOB_DEFINITIONS`；[作业模型](../backend/yuxi/modules/background_jobs/models.py) 的 `BackgroundJobRecord`；[JobTracker](../backend/yuxi/modules/background_jobs/service.py)；[worker 启动与恢复](../backend/yuxi/bootstrap/worker.py)。具体任务状态转移应继续查相关服务和测试。

### 2.11 测试目录：按风险选证据

> 原文位置：[ARCHITECTURE.md 第 74 行](../ARCHITECTURE.md#L74)。


**原文要点：**后端测试位于 `backend/test`，分为 unit、integration、e2e；新增或修改行为时，测试放在最能覆盖实际风险的层级。

- **unit（单元）**：检查一个小函数或模块的逻辑；通常快，但不能自动证明真实数据库或网页行为。

- **e2e（端到端）**：从较接近真实用户的入口走完整链路，检查最终状态；成本通常更高，也仍有覆盖范围限制。

## 前端代码地图

原文位置：[ARCHITECTURE.md 的“前端代码地图”](../ARCHITECTURE.md#前端代码地图)。这一节解答：用户看见的网页从哪里启动，代码按什么职责分组，又怎样把用户操作交给后端。这张地图列出目录职责和主要入口。

### 前端是什么？Vue 和 Vite 各负责什么？

> 原文位置：[ARCHITECTURE.md 第 78 行](../ARCHITECTURE.md#L78)。


> 原文：前端是 Vue 3 + Vite 应用，业务入口集中在 `frontend/src`。

**通俗解释。** 前端是浏览器里显示的页面和运行在浏览器中的界面逻辑：输入框、对话列表、按钮、加载状态等。Vue 是编写并组织这些界面的框架；Vite 则提供开发时的服务器和构建工具。`frontend/src` 是前端源码的主要目录，`src` 是 source（源代码）的缩写。Vue 负责“怎么组织界面”，Vite 负责“开发时怎么运行、发布前怎么构建”；它们并不替代后端处理权限或保存数据。

**代码入口。** [frontend/package.json](../frontend/package.json) 的 `scripts` 可看到 `vite serve` 和 `build`，依赖列表中可看到 Vue；[frontend/index.html](../frontend/index.html) 中的 `<div id="app">` 是应用放入网页的位置。

### 1. 应用从哪里启动？`app/main.js`、`App.vue`、路由和布局

> 原文位置：[ARCHITECTURE.md 第 80 行](../ARCHITECTURE.md#L80)。


> 原文：`app/main.js` 挂载应用，`app/App.vue` 提供主题与根 RouterView，`app/router` 与 `app/layouts` 拥有路由、访问守卫和应用导航。

**整体意思。** 先创建并启动网页应用，再根据浏览器地址决定显示哪个页面，并套用对应页面布局。**Router（路由）**是“地址和页面的对应关系”，例如访问 `/agent` 时显示聊天工作区；**布局（layout）**是多个页面共用的侧边栏和内容区域等页面骨架；**主题**是浅色、深色等全局视觉设置。**RouterView** 是告诉 Vue“在这里显示当前路由对应页面”的位置。

应用入口 [main.js](../frontend/src/app/main.js) 中可以先只看：

```js
const app = createApp(App)
app.use(router)
app.mount('#app')
```

这三步分别是创建 Vue 应用、启用路由、把应用放到 HTML 的 `#app` 元素中。这里 Vue 的 `mount` 是把界面放进网页；它不同于 Docker 把宿主机文件夹挂载到容器。

**访问守卫是什么？** 可以把它理解成进入某个网页前的一次前端检查，例如未登录时引导到登录页。它只控制正常网页体验，不能替代后端权限检查：有人可以不点网页按钮而直接请求 API。

**代码入口。** [App.vue](../frontend/src/app/App.vue) 查看根组件、主题与页面显示；[路由 index.js](../frontend/src/app/router/index.js) 查看 `/agent` 和 `beforeEach`；[AppLayout.vue](../frontend/src/app/layouts/AppLayout.vue) 查看应用导航与页面布局。

### 2. 页面层：`pages` 和 `AgentView`

> 原文位置：[ARCHITECTURE.md 第 81 行](../ARCHITECTURE.md#L81)。


> 原文：`pages` 是路由适配与页面装配入口。`AgentView` 把路由选择交给串行协调器，并装配会话工作区与智能体选择器。

**整体意思。** `pages` 中的文件是用户进入某个地址后对应的页面；页面负责把需要的组件拼在一起。“装配”就是组合已有组件，不意味着所有业务细节都直接写在页面里。

以 `/agent` 为例：[路由配置](../frontend/src/app/router/index.js) 选择 `AgentView`；[AgentView.vue](../frontend/src/pages/AgentView.vue) 在模板里组合 `SessionWorkspace`（会话工作区）和 `SessionAgentPicker`（智能体选择器）。页面中的 [threadRouteCoordinator.ts](../frontend/src/pages/agent/threadRouteCoordinator.ts) 帮助按顺序协调路由切换时的选择与加载。

**为什么需要串行协调？** 假设用户快速从会话 A 切到 B：A 的加载响应可能比 B 晚返回。如果不处理顺序和过期结果，界面就可能已经在 B，却显示 A 的内容。这里是为了理解设计目的的典型场景，具体边界应看协调器代码与测试；不能从名字推断它解决了所有异步问题。

### 3. `modules`：按业务把界面与逻辑放在一起

> 原文位置：[ARCHITECTURE.md 第 82 行](../ARCHITECTURE.md#L82)。


> 原文：`modules` 按 session、agents、projects、workspace、knowledge、extensions、identity、settings、background-jobs、dashboard 组织业务；`ui` 拥有界面，`model` 拥有状态与领域逻辑……

**术语。** `module` 是模块，`domain` 是业务领域。`ui` 多放负责显示和交互的组件，`model` 多放状态及业务处理逻辑。这是项目划分界面与状态逻辑的主要方式；阅读一个功能时可以沿页面、组件和状态模块追踪。

| 模块名 | 可以先理解成 |
|---|---|
| `session` | 会话内容、输入队列、事件流、审批和提及等 |
| `agents` | 智能体目录、选择和编辑 |
| `projects`、`workspace` | 项目及用户工作空间 |
| `knowledge`、`extensions` | 知识库，以及工具、MCP、Skills 等扩展 |
| `identity`、`settings` | 用户身份和设置 |
| `background-jobs`、`dashboard` | 后台作业和数据总览 |

例如，对话区界面在 [SessionWorkspace.vue](../frontend/src/modules/session/ui/SessionWorkspace.vue)；会话输入相关逻辑可从 [sessionInput.js](../frontend/src/modules/session/model/sessionInput.js) 入手。**SSE** 是服务端通过持续的 HTTP 连接向浏览器发送一条条事件的方式；**Input 排队** 是请求已提交但可能还没有被正式消费；**审批** 是遇到需要人决定的操作时等待回答；**提及** 是用户在输入中引用某种资源。它们都属于会话体验，但不是同一个功能。

### 4. `shared`：不属于某个业务的共用部件

> 原文位置：[ARCHITECTURE.md 第 83 行](../ARCHITECTURE.md#L83)。


> 原文：`shared/ui` 与 `shared/lib` 保存通用界面和工具，`shared/model` 保存主题状态；全局样式集中在 `assets/css`，颜色和基础规范复用 `base.css`。

**整体意思。** 某些界面组件、工具函数或主题设置可能被多个业务页面使用，可以放在 `shared`（共享）区域。`ui` 是界面，`lib` 是可复用工具代码，`model` 是共享状态。全局 CSS 定义页面样式；CSS 变量可以统一颜色与间距，避免不同页面出现各自维护的一套值。

**为什么分开？** 如果知识库页面和聊天页面都要用同一个通用组件，共用实现更方便保持一致；如果某逻辑只为一个业务服务，强行放进 `shared` 反而会让边界不清。

**代码入口。** [shared/ui](../frontend/src/shared/ui) 查看共用组件；[shared/lib](../frontend/src/shared/lib) 查看工具；[主题状态 theme.js](../frontend/src/shared/model/theme.js)；[base.css](../frontend/src/assets/css/base.css) 查看基础样式变量。

### 5. `apis` 与模块边界：网页怎样请求后端？

> 原文位置：[ARCHITECTURE.md 第 84 行](../ARCHITECTURE.md#L84)。


> 原文：`apis` 是集中 HTTP 边界，复用 `base.js` 的请求、鉴权和错误处理。模块不能依赖 app/pages，shared 不能依赖业务模块或 API……

**整体意思。** 前端与后端主要通过 HTTP 请求通信；项目把普通请求集中放到 `apis`，共用 [base.js](../frontend/src/apis/base.js) 中的请求、认证和错误处理。比如 [agent_api.js](../frontend/src/apis/agent_api.js) 包含会话和智能体相关请求，而不是每个界面组件都独自拼接口地址。

**边界是什么意思？** `app/pages` 更接近应用入口和具体页面；`modules` 放业务能力；`shared` 放更通用的能力。如果通用组件反过来依赖某个具体页面，就很难再被其他页面复用。跨业务模块调用要走公开入口或公开 UI 组件，而不直接依赖对方内部的 `model/` 文件。`@/` 是源码路径别名，便于写导入路径，不是网络地址。

**ESLint** 是前端代码静态检查工具，项目用它检查部分导入边界，包括路径别名、相对路径和动态导入。**动态导入**是在程序运行到某处时再加载模块。规则见 [frontend/AGENTS.md](../frontend/AGENTS.md) 和仓库的 ESLint 配置；修改导入路径后可以运行检查，定位违反依赖方向的代码。

### 6. TypeScript、会话状态、输入与草稿

> 原文位置：[ARCHITECTURE.md 第 85 行](../ARCHITECTURE.md#L85)。


> 原文：新 TypeScript 逻辑经 strict 类型检查，build 先执行 typecheck；现有 JavaScript 逐步迁移。`sessionRuntime` 按 Thread 拥有一份 item 状态……

**类型检查。** JavaScript 和 TypeScript 都能写网页逻辑；TypeScript 增加了类型描述与检查，例如提醒开发者不要把字符串当作数字使用。项目的 `strict` 是较严格的检查模式；[tsconfig.json](../frontend/tsconfig.json) 配置了 `strict`，[package.json](../frontend/package.json) 的 `build` 先运行 `typecheck` 再构建。类型检查能提前发现一类错误，但不能替代真实运行测试。

**为什么要有统一会话状态？** 同一个会话的内容可能来自历史分页、实时 SSE 和断线恢复快照。如果三个入口各自维护一份互不协调的列表，页面可能重复显示、丢消息或串会话。这里的 **Thread** 指一条会话，**item** 指展示中的消息或其他会话条目，**reducer** 是按事件和当前状态计算下一状态的处理逻辑。本项目让 `sessionRuntime` 按 Thread 管理状态，展示内容从统一状态按需派生；不应把它理解为数据库里的最终事实都存在浏览器内。

**输入与草稿。** `sessionInput` 负责固定本次提交内容、为重试复用幂等身份，并处理接收后的交接：比如用户点击发送后又编辑输入框，已经发送的那份内容不能跟着变化；网络异常重试时，也不能意外制造另一份同样的输入。输入队列观察者确认后端已消费 Input 后触发运行状态恢复，共享 runtime 再依据当前 Turn 选择对应的运行订阅。`SessionWorkspace` 负责编辑器草稿、附件及面板；视图存活期间各自的草稿分别保留，首次进入 Thread 时从持久草稿初始化。

**代码入口。** 从 [sessionRuntime.js](../frontend/src/modules/session/model/sessionRuntime.js) 看 `useSessionRuntimeStore`；从 [sessionInput.js](../frontend/src/modules/session/model/sessionInput.js) 看 `createSessionInput` 内 `frozen` 和 `idempotency_key`；从 [SessionWorkspace.vue](../frontend/src/modules/session/ui/SessionWorkspace.vue) 看两者怎样被页面使用。前端结构后续演进的讨论见 [重构提案](../docs/develop-guides/decisions/proposed/2026-09-30-agent-view-frontend-refactor.md)，提案不自动等于已经实现的行为。

### 7. 页面入口和权限分别在哪里生效？

> 原文位置：[ARCHITECTURE.md 第 87 行](../ARCHITECTURE.md#L87)。


> 原文：`/` 是公开首页；登录后的核心工作区是 `/agent`。`/extensions` 对所有登录用户开放……后端权限检查始终是最终边界，前端守卫只负责页面体验。

`/` 是不要求登录的首页；`/agent` 是需要登录的聊天工作区；`/extensions` 提供扩展入口。登录用户可以看到 Skills 与个人 MCP 连接；知识库和工具管理、MCP 全局配置、Dashboard 又有更高角色要求。**管理员**与**超级管理员**是项目中的不同角色，不能因为能打开扩展页，就推断能修改所有配置。

## 智能体运行链路

原文位置：[ARCHITECTURE.md 的“智能体运行链路”](../ARCHITECTURE.md#智能体运行链路)。这一章跟随“用户发送一条普通消息”的主要路径。它比最简单的聊天程序复杂，是为了在多用户、排队、失败恢复、审批和文件等场景下，仍能知道“谁提交了什么、谁正在执行、结果属于哪次执行”。下列十步中的协作、审批、文件等是相关能力与分支，**不是每条普通消息都会全部触发**。

先认识几个反复出现的名称：

| 名称 | 入门理解 |
|---|---|
| Session / Thread | 项目接口中用来组织一次会话及其历史的身份；阅读源码时注意各处命名。 |
| Input | 一次接收的用户输入；排队时也保留自己的身份。 |
| Receipt | 接收回执，记录该次请求接收及重试所需的事实。 |
| Message | 正式保存的消息记录。 |
| Turn | 一轮业务工作及其最终结果的边界。 |
| Run | Turn 中实际执行的一段运行；等待后恢复可能形成新的 Run。 |
| Project / Workdir | 项目资源 / 它绑定的持久工作目录，用于文件操作。 |
| Artifact | Agent 生成并交付的文件等产物。 |

这些是本项目建模方式，不能将不同项目里的同名词自动视为相同概念。

### 第 1 步：网页收集内容并提交

**通俗解释。** 用户在对话界面输入文本、选择图片或附件，也可能选择模型与工具审批模式。`AgentView` 负责页面装配，`SessionWorkspace` 负责工作区中的输入和展示，前端 API 模块把数据发到后端。

**Public Session API** 是项目提供的会话接口，不代表浏览器无需登录：访问仍受身份与权限约束。**投影（projection）**指从保存的事实整理出某个供读取的视图；项目让 Session 的详情、列表、搜索和更新响应采用一致的投影方式，减少各页面看到互相矛盾的会话信息。

### 第 2 步：后端确认身份并保存原始输入

> 原文位置：[ARCHITECTURE.md 第 94 行](../ARCHITECTURE.md#L94)。


> 原文要点：Public API 将 JWT 或 API Key 身份转为 `ActorScope`；接入事务锁定 Thread、验证作用域与幂等回执，保存 Input、Receipt 和附件绑定，接收时冻结配置。

**解释。** JWT 是一种常用于表示已登录身份的令牌；API Key 是外部调用所用的凭据。`ActorScope` 表示这次请求的可信身份和作用范围。**锁定 Thread** 可以先理解为对该会话的关键操作进行并发协调，防止两个请求同时修改时出现冲突；具体锁语义以数据库事务及代码为准。

用户点一次发送，网络断开后可能点击重试。系统使用 **idempotency key（幂等键）**识别同一次请求，并用 Receipt 记录接收事实；同一个键不能被当作任意不同内容的万能通行证。原始正文、附件引用和本次配置选择被保存；“冻结配置”意味着当前输入采用接收时确定的快照，不应因之后改了智能体设置而悄悄改变已接收输入。

在 [events.py](../backend/yuxi/api/routers/public_v1/agents/events.py) 看 `submit_public_event` 接收事件和幂等键；[inputs.py](../backend/yuxi/modules/agents/services/inputs.py) 看 `accept_message` 如何验证、检查回执、锁定会话并提交。该接口中的 `202` 表示已持久接收，不代表模型回答已经生成。

**对照代码。** [接收消息服务](../backend/yuxi/modules/agents/services/inputs.py#L255)在完成前面的输入处理后有以下几行：

```python
await db.commit()
await dispatch_next_input(uid=scope.uid, agent_slug=agent_session.agent_id, thread_id=agent_session.thread_id)
return _accepted(receipt)
```

`db.commit()` 提交数据库中的接收事实；`dispatch_next_input(...)` 继续尝试调度；`_accepted(receipt)` 把接收结果整理后返回。`await` 表示等待该异步操作完成。这里只截取这一条执行路径的末尾；读取上方代码还能看到失败和幂等重放等其他分支。

### 第 3 步：选择待处理输入并创建一轮运行

> 原文位置：[ARCHITECTURE.md 第 95 行](../ARCHITECTURE.md#L95)。


> 原文要点：调度器锁定 Thread 后领取未暂停队列的就绪优先队头，原子创建 Turn、首个 pending Run 和正式 Message；follow-up 与 steer 使用不同调度规则。

**解释。** 用户输入先保存为 Input，不一定马上执行。**调度器 scheduler** 决定现在应该处理哪个输入；**pending** 表示待处理；**原子创建**在这里指相关记录在同一事务中一起提交或回滚，避免只留下半套数据。

`follow_up` 是后续普通输入，按 **FIFO（先进先出）**逐条派发；`steer` 是改变当前工作方向的引导，具有优先规则。项目会按接收顺序合并连续且已就绪的 steer 前缀；不能把分隔或尚未就绪的输入随意跳过。每个 Input 仍有独立身份。

队列暂停和恢复也有各自事实：`queue_control.py` 依据待办决定暂停，调用用例负责会话锁、事务与恢复意图，Input 模型负责恢复标记、repository 负责排序。暂停后用户主动提交的恢复消息按项目规则优先且单独消费，处理完继续原队列。消费时会绑定 Input 的执行归属，并把附件关联到该 Input 对应的最后一条正式 Message；Receipt 保留原请求的命令目标，不事后猜写成执行归属。`received_at` 是接收时间，`created_at` 表示进入执行投影的时间。正在等待用户回答或审批时，不接受普通消息。

**为什么要这么细？** 假设用户多次补充问题并上传附件，如果只存一个“最新消息”，就难以可靠说明哪次输入被哪次运行消费、附件属于哪条消息。以上是阅读动机；具体边界请以代码为准。

**源码入口。** [scheduler.py](../backend/yuxi/modules/agents/services/scheduler.py) 的 `claim_next_input`；[input.py repository](../backend/yuxi/modules/agents/repositories/input.py) 的 `ready_batch`；[queue_control.py](../backend/yuxi/modules/agents/services/queue_control.py) 查看暂停；[inputs.py](../backend/yuxi/modules/agents/services/inputs.py) 查看原始输入和回执。

**对照代码。** [claim_next_input](../backend/yuxi/modules/agents/services/scheduler.py#L51) 先取得符合规则的一批待处理输入：

```python
input_repo = AgentInputRepository(db)
batch = await input_repo.ready_batch(thread_id=agent_session.thread_id, uid=agent_session.uid, app_id=agent_session.app_id)
if not batch:
    return None
```

`input_repo` 负责输入记录的数据访问；`ready_batch(...)` 按会话和用户等范围选择已就绪输入；如果没有可领取的输入，函数就返回 `None`。这之前还有队列暂停、运行清理等检查，之后才建立 Turn 和 Run；不能仅凭这几行理解完整调度规则。

### 第 4 步：数据库提交后，再交给后台队列

> 原文位置：[ARCHITECTURE.md 第 96 行](../ARCHITECTURE.md#L96)。


> 原文要点：拥有事务的代码提交后才向 ARQ 投递 pending Run；恢复扫描可补投未成功投递的同一个 Run，不自动重试已经失败的工作。

**术语。** 事务（transaction）是数据库里一组操作的提交单位；commit 是让这组记录正式生效。ARQ 是使用 Redis 支持后台任务投递的工具。此处的数据库 commit 不是 Git 提交。

**为什么先提交再投递？** 如果任务先进入队列，worker 可能马上读取数据库，却发现 Run 还没提交。正确顺序避免了这个时序问题；但提交后网络或队列仍可能出错，因此还需要后续恢复扫描。**补投未成功投递的同一个 Run** 和 **自动重做已经失败的业务工作** 是两件事；项目文档明确只承诺前者，不等于失败任务一定自动再执行。

**追问：提交后、投递前断电会怎样？** [scheduler.py 的 `dispatch_next_input`](../backend/yuxi/modules/agents/services/scheduler.py#L70) 在数据库会话上下文中领取输入并创建 Run；退出上下文时，[数据库会话管理器](../backend/yuxi/infrastructure/postgres/manager.py)提交事务。随后代码才执行：

```python
delivered = await deliver(dispatch) if dispatch is not None else True
```

若 Run 已提交，而 `deliver` 发布队列失败或进程在此之前退出，数据库里的 Run 仍为 `pending`。`recover_pending_dispatches` 扫描这些记录，核对会话、用户、应用和 Run 状态后，再发布**同一个 Run ID**。若 worker 已经执行而最终标记为 `failed`，它已不是等待补投的 pending Run；此恢复扫描不会因此自动重做失败的业务操作。有关恢复与幂等的通用概念，可以回看 [开发规范学习笔记](开发规范学习笔记.md)。

### 第 5 步：worker 获取执行权并准备运行

> 原文位置：[ARCHITECTURE.md 第 97 行](../ARCHITECTURE.md#L97)。


> 原文要点：worker 用 identity 与 job-attempt token 取得 Run lease；复核输入、用户、Workdir，维持心跳，准备 Context 和 write-once 清单后进入 LangGraph。

**术语逐个拆开。** worker 是后台执行程序；identity 是执行进程身份；attempt token 区分某次任务尝试；lease 是有有效期的执行权；heartbeat（心跳）是定期证明仍在工作的信号。重复任务没有取得有效执行权时不能同时执行。**Workdir 授权**是确认该运行有权使用指定工作目录。

**追问：worker 领到任务后失联怎么办？** 假设 worker A 领取 Run 时登记了自己的身份和租约到期时间；运行期间，心跳会尝试延长租约。续租时，[`renew_lease`](../backend/yuxi/modules/agents/repositories/runs.py#L473) 检查运行状态、worker 身份和到期时间：如果 A 已失联到租约过期，旧身份不能继续续租。恢复处理在锁内再次确认到期后，将 Run 标记为 `failed`、记录 `worker_lease_expired` 并标记运行环境待清理，见 [`reconcile_expired_lease`](../backend/yuxi/modules/agents/repositories/runs.py#L557)。

这时外部工具可能在失联前已经产生效果，也可能没有；例如发送请求后没收到回执，必须根据第三方回执或幂等机制核对。这里的失联收敛也不同于上一步对 pending Run 的补投。

**Context** 是此次运行所需的配置和运行信息，例如模型和可用资源；**manifest（运行清单）**概括准备结果，`write-once` 表示首次记录后按项目规则不能随意改写。准备阶段在有效 lease 下写入清单，才进入 LangGraph。验证失败走受控的拒绝与结算路径，而不是假装执行成功。

**Langfuse** 是可选的远端观测能力：`trace` 可以理解为一次工作的一条观测链，`observation` 是其中更细的观测记录；这里按 Turn 和 Run 做关联。远端观测用于了解过程，不拥有业务最终状态，最终事实仍由项目持久化规则决定。

**代码入口。** [runner.py](../backend/yuxi/modules/agents/services/runner.py) 找 `_process_agent_run` 和 `_heartbeat_lease`；[preparation.py](../backend/yuxi/modules/agents/services/preparation.py) 找 `prepare_and_record_run_execution`；[ChatbotAgent graph.py](../backend/yuxi/modules/agents/runtime/agent_backends/chatbot/graph.py) 看模型与工具怎样被组装。

**对照代码。** 当运行 Context 已准备好时，[ChatbotAgent 的构图代码](../backend/yuxi/modules/agents/runtime/agent_backends/chatbot/graph.py#L104)会装配工具和提示词，并将它们交给 Agent：

```python

prompt = build_prompt_with_context(context)
middlewares = await _build_middlewares(context, backend)
```

这三行分别解析本次运行的工具、组织提示词、准备中间件；紧接着的 `create_agent(...)` 再组合模型和这些结果。模型在上方代码中加载，工具是否真的可用还取决于配置与权限。这里解释的是组装步骤，不等于每轮都会调用某个工具。

### 第 6 步：组装智能体能力，必要时协作

> 原文位置：[ARCHITECTURE.md 第 98 行](../ARCHITECTURE.md#L98)。


> 原文要点：Session 通过同一 Agent 后端及 middleware 组合 Workdir、Skills、MCP、审批、摘要和协作能力；成员各自有身份和执行状态，可以共享项目工作目录。

**基本概念。** middleware（中间件）是运行流程中负责某类横切工作的组件，例如权限检查或摘要；Skill 是能力说明及可能的依赖；MCP 是连接工具服务的协议。把这些能力与当前模型、用户和工作目录组合后，才形成这一轮可执行的 Agent。

**协作不等于把所有历史混在一起。** 项目文档说明，协作成员各有 Thread/Input/Turn/Run 和上下文，通过父子关系及名称关联，不继承父历史；协作工具也可创建继承当前项目的独立顶层对话，并在同用户和 APP 作用域内跨树协作。稳定 ID 用于全范围寻址，路径只在本树内解析。

同树共享 Project Workdir；文档描述的 `max_cooperation_concurrency` 默认值是 4，限制执行名额。使用 **Cube** 后端时同一用户的多棵树共用该用户的 Cube VM，等待资源时会释放 worker 与执行名额；不要把 Cube 的 VM 规则套到本机的 Container 后端。PostgreSQL 保存协作、等待和终态事实；普通取消只影响指定 Turn，用户显式停止才停止整棵协作树。各 Run 的租约、结果和终态独立。用户环境在无活动 Run 或操作时可以空闲休眠；持久工作目录与内存连续性是不同问题。

**源码入口。** [cooperation.py](../backend/yuxi/modules/agents/services/cooperation.py) 看协作服务；[cooperation middleware](../backend/yuxi/modules/agents/runtime/middlewares/cooperation.py) 看运行时能力；[会话协作文档](../docs/agents/session-cooperation.md) 看完整行为。

### 第 7 步：安全接管、等待与恢复

> 原文位置：[ARCHITECTURE.md 第 99 行](../ARCHITECTURE.md#L99)。


> 原文要点：steer 在安全接管点消费；旧 Run `yielded` 后同一 Turn 创建下一 Run。人工等待使 Run `interrupted`、Turn `waiting`，回答或审批后继续同一 Turn。

**先看场景。** 假设 Agent 正在执行任务，你补充“请改成中文回答”。系统不能把新指令直接塞进任意一个执行到一半的工具调用里；项目设置了**安全接管点**：工具批次与 checkpoint（执行状态检查点）保存后，或没有工具时模型调用完成后。这样的时点让系统有机会先记录上一段实际做了什么，再接续新指令。

待处理的 steer 按规则固定为消费批次；旧 Run 记为 `yielded`（让出），同一 Turn 新建下一 Run。事务提交后，还要确认旧运行环境的清理责任已完成，再投递接续；同一 Thread 仍有未完成运行清理时，领取边界会拒绝新启动。普通工具循环如果没有这些接管或等待情形，仍属于同一 Run。

另一个场景：工具需要用户批准。此时 Run 的 `interrupted` 表示当前执行中断等待，Turn 的 `waiting` 表示这一轮仍在等待；系统保存与该 Run 对应的**等待点**。用户结构化回答或作出审批决定后，消费等待点，并在同一 Turn 创建新的 Run 继续。这与“用户又发出一个普通问题、开启全新一轮”不是同一个行为。

**为什么需要归属和清理？** 否则可能把审批结果送到错的任务，或前一段执行仍在操作文件时下一段已经开始。

**源码入口。** [run_lifecycle.py](../backend/yuxi/modules/agents/services/run_lifecycle.py) 搜索 `settle_checkpoint`、`_consume_steer`、`complete_run_runtime_cleanup`；[turns.py](../backend/yuxi/modules/agents/services/turns.py) 看 `resume_turn`；[steer middleware](../backend/yuxi/modules/agents/runtime/middlewares/steer.py) 是运行中安全接管相关入口。

### 第 8 步：确定完成、失败或取消的最终归属

> 原文位置：[ARCHITECTURE.md 第 100 行](../ARCHITECTURE.md#L100)。


> 原文要点：当前 owner 在数据库事务中收敛 Run 和 Turn；最终回答指向明确的顶层 result Run；取消与失联恢复各有规则，外部副作用仍按至少一次语义核对。

**什么叫“收敛终态”？** 一段 Run 成功、失败或取消后，把它和所属 Turn 的结果按规则保存成明确状态。**当前 owner** 是仍持有效执行权的负责人；一个旧 worker 不能在失去执行权后继续覆盖新状态。

一轮的最终回答必须来自明确指定的**顶层 result Run**的输出 Message；模型和工具的审计记录也要保留各自 Run 的归属。普通历史只读取已经登记可以公开展示的条目，不把内部 prompt 或 checkpoint 当成普通聊天记录。这样即使有子任务、多次恢复或相邻运行，也不需要靠“最近出现的一条消息”猜答案是谁的。

协作时，父任务完成、失败或单轮取消，不自动替子任务做最终决定；用户明确停止整棵协作树才按树范围取消在途 Turn。普通取消先把状态写入持久存储并暂停待消费队列，再使用 Redis 信号加快通知；信号本身不是最终事实。worker 失联后通过租约核对（lease reconciliation）使失联 Run 形成可观察的失败结局。

**至少一次（at-least-once）是什么意思？** 某些外部操作可能因为网络超时或恢复被重复尝试；不能仅凭本地状态就保证第三方只收到了恰好一次。涉及发邮件、写外部系统等副作用，应依据具体接口的幂等键、回执或实际状态核对。

**源码入口。** [run_lifecycle.py](../backend/yuxi/modules/agents/services/run_lifecycle.py) 看 `settle_run` 和 `reconcile_expired_run`；[turns.py](../backend/yuxi/modules/agents/services/turns.py) 看取消及读取轮次；[cooperation.py](../backend/yuxi/modules/agents/services/cooperation.py) 看树级控制；[public_items.py](../backend/yuxi/modules/agents/services/public_items.py) 看公开条目投影。

### 第 9 步：记录工具过程，并把事件流发送到网页

> 原文位置：[ARCHITECTURE.md 第 101 行](../ARCHITECTURE.md#L101)。


> 原文要点：工具开始、进度和最终结局来自不同观察点；模型/工具消息写入持久事实，Redis 保存公开事件，SSE 传输事件，断线时按游标或快照恢复。

**先区分三个问题：**工具是否真的开始执行？执行最后成功还是失败？网页能否看到并在断线后恢复这些信息？它们相关，但不是同一件事。

- 工具真实开始和进度来自 `BaseTool` 的**回调**：回调可以先理解为“某个动作发生时通知观察者”。
- 最外层 `ToolErrorGuardMiddleware` 根据最终 `ToolMessage` 发布结局。原始结果和最终结果都成功时，保留压缩前原文；中间件直接返回结果但工具没有真实开始时，不应伪造 `started_at`。`BaseAgent` 再把它转为统一工具事件。
- LangGraph v3 的 `ProtocolEvent` 可先理解为运行协议中的模型/工具事件；`RunMessageRecorder` 负责统一记录对应的消息事实。
- 工具审计把原始结果放在 `extra_metadata.output`，`content` 按约束保持为空；数据库约束负责保护这种存储规则。审计文本、Memory 和公开内容从相同的工具结果契约派生，再由公开适配器转换为 OpenAI Agents 格式的事件。Memory 是项目给 Agent 使用的记忆能力，并不等于浏览器缓存。
- 消息事实、公开快照各自在相应提交后发布事件；checkpoint 属于独立的执行结果。Redis 保存逐条公开事件，SSE 的 `data` 放事件本身。**逻辑 event_id** 用于标识事件，**恢复 cursor** 用于告诉服务端从哪个进度继续，两者不能混成一个概念。
- 网络断开或短期事件已过期时，客户端按协议继续订阅或回读 PostgreSQL 快照；不能把隔壁 Run 的输出猜成当前 Run 的结果。

**为什么这么设计？** 用户看到的“工具正在执行”“工具失败”“这轮回答是什么”需要与真实执行和归属相符；实时流可能断线，但持久事实不能只存在临时网络连接里。

**代码入口。** [tool_error_guard.py](../backend/yuxi/modules/agents/runtime/middlewares/tool_error_guard.py) 看工具回调和错误守卫；[message_recorder.py](../backend/yuxi/modules/agents/services/message_recorder.py) 看消息记录；[messages.py 模型](../backend/yuxi/modules/agents/models/messages.py) 看审计约束；[event_writer.py](../backend/yuxi/modules/agents/services/event_writer.py) 看事件写入；[subscriptions.py](../backend/yuxi/modules/agents/services/subscriptions.py) 和 [HTTP events.py](../backend/yuxi/api/routers/public_v1/agents/events.py) 看 cursor、订阅及断线恢复。

### 第 10 步：会话属于哪个 Project，文件保留在哪里？

> 原文位置：[ARCHITECTURE.md 第 102 行](../ARCHITECTURE.md#L102)。


> 原文要点：Thread 保存不可变 `project_id`，Project 绑定 `workdir_path`；managed 和 linked 项目有不同目录来源，删除、归档和文件访问有明确边界。

**解释。** Project 是项目资源，Thread 是归属于项目的对话。`project_id` 是项目标识，原文说不可变，意味着已经创建的 Thread 不应随意改绑到另一个项目。每个 Project 绑定一个 `workdir_path`（工作目录路径）；多个 Project 允许绑定到同一个路径，因此“两个项目”不自动等于“两份完全不同的物理目录”。

- **managed Project**：工作目录由服务端按类似 `projects/YYYYMMDD/<六位标识>[-N]` 的规则创建和管理。
- **linked Project**：绑定该用户 `UserWorkspace` 中已有目录。
- **no-follow**：处理路径时不盲目跟随符号链接，以免通过链接绕过被允许的目录边界；实际安全行为要看具体文件操作和平台约束。
- **归档**：把 Thread 标记为归档，不等于直接删除其持久内容。删除 Project 前，如果仍有活跃 Turn 或待处理 Input，项目会拒绝；允许后软删除 Project 并归档所属 Thread。**软删除**通常指保存删除状态而不是立即物理擦除所有记录。
- `workspace` 模块负责宿主路径和基于文件描述符的相对文件操作（`fd-relative`）：可以先理解成以已经打开且经过验证的目录为基准操作，减少简单路径拼接带来的边界问题。Workdir resolver 为 Viewer（文件查看）、附件、Artifact、Run 和协作会话解析一致的持久工作目录。
- Run 进入终态并完成清理后，解除当前执行的清理责任；按原文所述，用户 VM 在没有活动 Run 或命令时可空闲休眠，Workdir 保留。VM 的内存、运行中的进程和持久目录不是同一类状态；具体后端差异应查沙盒文档。

**为什么要划分 Project、Thread 和 Workdir？** 用户可能针对同一项目开多个对话，而不同对话可以共享需要处理的文件；但资源归属、执行状态和持久文件不能因此混为一谈。目录路径是安全边界的一部分。

**源码入口。** [项目服务 projects.py](../backend/yuxi/modules/workspace/services/projects.py) 看创建与 `delete_project_view`；[bindings.py](../backend/yuxi/modules/workspace/services/bindings.py) 看 `WorkdirBinding` 与授权解析；[paths.py](../backend/yuxi/modules/workspace/paths.py) 看路径规范化和目录边界；[Project 模型](../backend/yuxi/modules/workspace/models.py) 查看持久字段定义。

### 十步放在一起看

```text
前端收集输入
  → 后端认证并持久接收 Input / Receipt
  → 调度器按规则领取，创建 Turn、Run、Message
  → 提交后投递后台队列
  → worker 取得执行权、准备 Context
  → 模型与按需工具执行（可涉及协作、沙盒或人工等待）
  → 保存归属明确的结果及状态
  → 事件逐步发给网页；断线时按协议恢复
```

这条图只表示主要方向，不是所有细节和严格的一次性直线：等待、接管、取消、恢复和协作有各自分支；Project / Workdir 贯穿涉及文件的多个步骤。建议先能用自己的话讲清这条主线，再按第 2～10 步逐个追源码和相关测试。

## 五、架构不变量：哪些规则不能被后续改动破坏

**原文位置：**[ARCHITECTURE.md：架构不变量](../ARCHITECTURE.md#架构不变量)。

**什么是不变量？**可以先理解成“无论系统经历什么正常操作，都要维持的规则”。例如“不同用户的私有数据不能互相读取”，并不是某个页面的视觉要求，而是系统的安全边界。这一章逐条说明 Yuxi 要维持的事实；理解每项规则时，可以结合后面的故障或并发场景，观察规则要保护什么。

### 不变量 1：开发环境以 Compose 描述为依据

> 原文位置：[ARCHITECTURE.md 第 106 行](../ARCHITECTURE.md#L106)。


> 原文要点（概括）：Docker Compose 是开发环境的事实来源；后端显式重启，前端保留热更新。

**通俗解释。** Compose 文件是开发环境的服务清单：服务怎么构建、怎么连接、端口和挂载怎样配置，都能在其中查到。本项目开发前端会监听源码变化；后端 `api` 和 `worker` 运行源码修改后，通常需要显式重启相应服务才生效。例如修改已挂载的 `src` 文件可由 Vite 热更新；修改依赖清单或镜像配置则要更新相应容器环境。

**为什么？**如果开发者以为代码已经生效，实际上容器仍运行旧进程，就可能误判功能或测试结果。先观察服务状态、日志和源码生效时点，能减少这类误会；不必默认再在宿主机启动一套独立后端。

**源码入口：**[Compose 中的 API](../docker-compose.yml#L61)、[worker](../docker-compose.yml#L121)、[frontend](../docker-compose.yml#L271)；前端开发监听见 [Vite 配置](../frontend/vite.config.js#L91)。

### 不变量 2：路由、业务流程和数据库访问分开

> 原文位置：[ARCHITECTURE.md 第 107 行](../ARCHITECTURE.md#L107)。


> 原文要点（概括）：HTTP 路由保持薄；业务流程在 `services`，数据库查询在 `repositories`。

**通俗解释。** HTTP 是浏览器和服务器通信的协议。Router（路由）接收请求、应用认证依赖并组装响应；Service（服务）编排“要做哪些业务步骤”；Repository（仓储）负责访问数据库。它们是职责划分，不是三个独立服务器。

**为什么？**如果在每个接口里重复写数据库和业务规则，增加另一个入口时容易出现两套不一致的实现。让业务规则有清晰归属，更容易复用和测试。

**源码入口：**[API 路由汇总](../backend/yuxi/api/routers/__init__.py)、[输入服务](../backend/yuxi/modules/agents/services/inputs.py)、[输入仓储](../backend/yuxi/modules/agents/repositories/input.py)。读时先区分“接收请求”“安排步骤”和“查询数据”，不必一次记住函数列表。

### 不变量 3：接收、消费、投递各有边界

> 原文位置：[ARCHITECTURE.md 第 108 行](../ARCHITECTURE.md#L108)。


> 原文要点（概括）：接收事务保存 Input 和 Receipt；消费事务生成 Message、执行和附件归属；提交后投递 ARQ；取消未消费输入不生成消息。

**通俗解释。** Input 是一次输入，Receipt 是接收回执；Message 是进入正式对话历史的消息。**接收**和**消费**是两个阶段：先记录用户交来了什么，再由调度器决定何时把它变成正式工作。事务是数据库中作为整体提交的一组操作；ARQ 是本项目用来投递后台任务的组件。

**为什么？**如果网页重复提交、用户在排队时取消，系统需要知道每次输入属于谁、是否已经消费，而不是因为重复请求创建多条错误消息。数据库唯一来源约束进一步防止同一输入被重复投影为同一类正式事实。事务提交后再投递也能避免 worker 抢先读取尚未提交的数据；但提交后投递仍可能失败，需要恢复补投。

**源码入口：**[接收输入 `accept_message`](../backend/yuxi/modules/agents/services/inputs.py#L187)、[调度和补投](../backend/yuxi/modules/agents/services/scheduler.py)、[Input 仓储](../backend/yuxi/modules/agents/repositories/input.py)。

### 不变量 4：排队要有顺序，改变方向要在安全时点

> 原文位置：[ARCHITECTURE.md 第 109 行](../ARCHITECTURE.md#L109)。


> 原文要点（概括）：同一作用域的 follow-up 按 FIFO 单条领取；steer 优先并合并连续就绪前缀；未就绪队头不能越过。

**通俗解释。** 这里的作用域包括用户、APP、智能体和 Thread（对话）。`follow-up` 是后续普通输入，FIFO 是先到先处理；`steer` 是要求正在执行的任务改变方向的输入。每次提交保留自己的身份，即使多个输入被消费到同一个 Run，也通过 `consumed_run_id` 明确记录归属。

**连续就绪前缀**可以先理解为：从按规则排好的队头开始，连续几条 steer 都已满足处理条件，才能合并为一批；碰到未准备好的队头不能跳过。**安全边界**是允许交接工作的时点，不等于模型生成任何一个字时都能随意打断。

**为什么？**用户连续补充信息时，系统必须有可解释的顺序，不能将两次提交悄悄合成一条原始记录，或把后面已经准备好的输入越过前面未就绪的输入。

**源码入口：**[输入仓储 `ready_batch`](../backend/yuxi/modules/agents/repositories/input.py#L107)、[运行生命周期与 steer](../backend/yuxi/modules/agents/services/run_lifecycle.py)。

### 不变量 6：运行必须有唯一负责人和有效租约

## 六、跨切面关注点：一个问题会经过哪些模块

**原文位置：**[ARCHITECTURE.md：跨切面关注点](../ARCHITECTURE.md#跨切面关注点)。

“跨切面”并不是新增一个服务，而是指配置、权限、数据、解析、观察这些问题会影响多个功能。理解它们时，要沿一条具体请求看各层如何配合。

### 关注点 1：配置从哪里来，修改后存在哪里

> 原文位置：[ARCHITECTURE.md 第 128 行](../ARCHITECTURE.md#L128)。


> 原文要点（概括）：Compose 和 `.env` 提供部署配置；管理员、用户及模型供应商设置以 PostgreSQL 为持久来源，Redis 是可失效缓存。

**通俗解释。** 部署配置决定服务怎样启动；平台里的某些设置由管理员或用户在运行中修改，保存到数据库。缓存是加快读取的临时副本，失效后需要依照项目机制重新读取主要来源。

**以管理员配置项为例。** [options.py](../backend/yuxi/modules/system/services/options.py) 的 `Option.resolve` 对一般字符串字段按数据库值、环境变量、默认值的顺序解析；列表和整数按各自的字段规则处理。`Option.get` 对可缓存项先尝试 Redis，缓存未命中再读 PostgreSQL；含敏感字段的配置不进入这一缓存。管理员保存时，`save_configuration` 先提交数据库，再使对应缓存失效。

**追问：旧读取会不会把旧值又写回缓存？** 假设请求 A 读到了旧数据库值，管理员随后保存新值并使缓存失效；如果 A 此时再把旧值写回，缓存就会倒退。项目读取时记录缓存版本，回填时用 Redis 脚本比较版本，只有版本仍相同才写入，见 `_save_cached_value`。这样一次具体的并发顺序就解释了为什么缓存除了过期时间，还需要版本检查。缓存失效操作本身失败时会记录警告；已写入 Redis 的配置缓存设置了 300 秒过期时间。

**源码入口：**[Compose 配置](../docker-compose.yml)、[系统设置服务](../backend/yuxi/modules/system/services/options.py)、[模型配置接口](../backend/yuxi/api/routers/models.py)。

### 关注点 2：权限从网页一直检查到数据访问

> 原文位置：[ARCHITECTURE.md 第 129 行](../ARCHITECTURE.md#L129)。


> 原文要点（概括）：前端路由和标签提供体验级约束；FastAPI 认证依赖与 repository 可见性查询提供最终授权。

**通俗解释。** 用户可能看不到某个按钮，但仍可直接构造请求；服务器要确认身份，再判断这个人能否访问具体资源。Repository 是数据访问层，查询时也要限制可见范围。

**为什么？**只隐藏页面而不限制后端，不能保护数据。前端检查仍有价值，它可以避免用户看到无法操作的按钮，但不能代替后端。

**源码入口：**[前端路由](../frontend/src/app/router/index.js)、[认证依赖](../backend/yuxi/api/dependencies/auth.py)、[知识库访问服务](../backend/yuxi/modules/knowledge/services/access.py)。

### 关注点 3：同一功能的数据分布在不同地方

> 原文位置：[ARCHITECTURE.md 第 130 行](../ARCHITECTURE.md#L130)。


> 原文要点（概括）：PostgreSQL 保存业务与知识元数据和唯一 LangGraph checkpoint；Redis 保存短期事件等；UserWorkspace 和 MinIO 保存各自负责的文件。

**通俗解释。** 元数据是描述数据的信息，例如文件归属和处理状态；文件字节是实际文件内容。数据库里“有一条文件记录”，不代表文件内容也存在同一张表里。UserWorkspace 持有工作目录和个人 Skill 的文件；MinIO 负责知识库与临时上传对象等。

**为什么？**排查“文件打不开”时，既要区分记录是否存在，也要查文件所在边界是否可读；备份和删除也需要了解各部分职责。数据库记录、文件和外部索引不一定自动形成一个事务。

**源码入口：**[Workspace 绑定](../backend/yuxi/modules/workspace/services/bindings.py)、[知识库上传服务](../backend/yuxi/modules/knowledge/services/uploads.py)、[PostgreSQL checkpoint](../backend/yuxi/infrastructure/postgres/checkpointer.py)。

### 关注点 4：对话附件和知识库文档走不同入口

> 原文位置：[ARCHITECTURE.md 第 131 行](../ARCHITECTURE.md#L131)。


> 原文要点（概括）：Agent 附件接收时绑定 Input 并准备进 Project Workdir；知识库上传先进入对象存储与元数据边界，再解析、分块和索引。

**通俗解释。** 用户在一次聊天中附加的文件，与用户建立长期知识库时上传的文件，都可能是 PDF，但它们的生命周期和用途不同：前者关联本次输入与工作目录；后者进入知识库处理和检索流程。

**为什么？**如果只因为文件类型相同就把两条路径混为一谈，会模糊文件归属、权限、保存位置和何时解析。解析器、分块方式和知识库连接器各自有接口边界；更换实现时需要适配对应接口，并检查权限与数据格式。

**源码入口：**[Agent 附件准备](../backend/yuxi/modules/agents/services/attachments.py)、[知识上传](../backend/yuxi/modules/knowledge/services/uploads.py)、[知识库机制](../docs/mechanisms/knowledge-base.md)。

### 关注点 5：排查时同时看过程和最终事实

> 原文位置：[ARCHITECTURE.md 第 132 行](../ARCHITECTURE.md#L132)。


> 原文要点（概括）：优先检查 Compose 的 `api`、`worker` 和依赖日志；Langfuse 参与观测；SSE 同时检查 Redis 事件和 PostgreSQL 终态。

**通俗解释。** **日志**是程序记录的运行信息；**观测**是收集和分析系统内部状态；Langfuse 是本项目用于追踪相关执行的信息服务；SSE 是服务端向浏览器持续推送事件的方式。

**怎么查“聊天页面卡住”？** 先根据会话和 Run 标识查看 PostgreSQL 中的状态：如果仍是 `pending`，继续查调度与队列投递；如果是 `running`，结合 worker 日志看执行和心跳；如果已经进入终态，但页面仍在等待，就检查前端 SSE 连接和 Redis 短期事件。启用 Langfuse 时，还可以沿关联的 Turn / Run 追踪模型和工具调用。这样每一步都在回答一个具体问题：任务停在哪一层、下一份证据在哪里。

**源码入口：**[可观测性模块](../backend/yuxi/infrastructure/observability)、[Agent 运行服务](../backend/yuxi/modules/agents/services/runner.py)、[readiness 检查](../backend/yuxi/modules/system/readiness.py)。
