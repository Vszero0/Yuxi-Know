### 【1.3】RAG、召回、排序与 Rerank

#### 【1.3.1】面试过程：约 03:24–06:43

**问题：** 什么是 RAG？为什么使用 Rerank？召回、排序和 Rerank 分别解决什么问题？

**当时回答的有效部分：** 知道初步检索后可重排候选，也提到 Embedding 分别编码和 Rerank 结合问题与文本评分；举出候选 50 条、重排后返回 10 条的例子。

**需要补强：** 先解释各阶段的目标和计算方式，再对齐面试官的术语。Rerank 是重新排序的操作，在 RAG 中可承担精排；有的推荐系统也会在精排后再进行列表重排，两种用法都存在。

#### 【1.3.2】RAG 的完整过程

```text
离线 / 入库：文档 → 解析 → 分块 → 文档 Embedding → 向量索引
在线 / 查询：问题 → 查询 Embedding / 关键词分析 → 检索候选
          → 融合 / 可选 Rerank → 组织上下文 → 模型生成 → 来源展示
```

RAG（Retrieval-Augmented Generation）先从外部知识中找候选证据，再让生成模型结合证据回答。工程问题包括解析质量、候选覆盖、排序、上下文长度、答案与证据是否一致。

#### 【1.3.3】召回：在大量数据中找候选

**What：** 以可接受的延迟从大集合找可能相关的内容，关注候选覆盖。目标片段没有进入候选集，后续排序模型就无法将它排上来。

**How：** BM25 对分析后的词项进行倒排检索和评分；向量召回将文档与问题分别编码，通过相似度和 ANN 索引找近邻；混合检索将多路候选融合。

**为什么各有价值：** BM25 适合名称、型号等字面词项；向量能处理一部分措辞不同但语义接近的情况；它们都受解析和分块质量影响。分词、错字以及模型语义表示都会影响召回。

**项目实现：** 查询向量检索时用知识库的 Embedding 模型编码用户问题，再以 COSINE 查询 Milvus；BM25 使用中文 analyzer 和稀疏索引。`IVF_FLAT` 的 `nlist=1024`、`nprobe=10` 控制分组与访问范围。输入问题的向量化发生在查询侧，文档向量则提前生成。

**指标：** Recall@K = 前 K 条命中的相关证据数 / 标注的全部相关证据数；Hit@K 看前 K 条是否至少命中一个相关证据。先看正确 chunk 是否进候选，再分析排序。

#### 【1.3.4】粗排、精排和 Rerank 的关系

```text
例如：100 万个 chunk → 召回 1000 → 粗排 100 → 精排 10 → 可选列表调整
```

数量只是示意。**粗排**使用向量相似度、关键词分数、轻量模型或简单特征快速筛选较多候选；**精排**对较少候选使用更复杂的评分，提高靠前结果质量。

**Rerank 是重新排序的操作，不是固定在精排之后的必选阶段。** 在常见 RAG 中，Rerank 模型对问题和候选文本评分，本身可以承担精排；在推荐系统中，精排后还可能按多样性、新鲜度、去重和业务规则再调整列表。

项目的典型路径是：向量 / BM25 / 混合检索 → 候选 → 可选 Rerank 模型 → 最终 Top K。简单系统的召回本身已有初步排序，不一定另有独立粗排服务。

**追问：为什么不让 Rerank 处理全部文档？** 它通常需要对每个问题—候选组合做额外计算，全量处理延迟和成本较高。先用高效索引筛选，再精排少量候选。

**追问：精排和 Rerank 的区别？** 精排强调一阶段的目标和计算预算；Rerank 强调对已有候选重新排序。RAG 中两者可以是同一步。如果对方说“精排之后再 Rerank”，先确认该系统精排的模型和后续重排的业务目标。

#### 【1.3.5】Embedding、重排模型和 Milvus WeightedRanker

Embedding 常见双编码思路：问题与文档分别编码，文档向量可预计算并索引；查询向量与其计算 COSINE 等相似度，快速产生候选。

重排模型接收问题和候选文本，并对每个问题—片段打分。交叉编码器将两者一起输入模型，能够考虑细粒度对应关系；重排也存在其他架构。模型分数是排序信号，不能直接当作正确率。

项目中 `WeightedRanker` 融合向量与 BM25 两路结果，是多路分数融合；可选 Rerank 模型进一步对问题和候选正文评分。见 [Milvus 检索实现](D:/Projects/Yuxi-Know/backend/yuxi/modules/knowledge/implementations/milvus.py) 与 [Rerank 实现](D:/Projects/Yuxi-Know/backend/yuxi/modules/models/rerank.py)。

**面试表达：** RAG 用外部检索提供证据。Milvus 负责快速召回，包含向量、BM25 和混合路径；可选重排模型对候选精排。排查时先判断正确证据有没有进入候选，再看排序，最后看生成是否正确使用证据。

参考：[Sentence Transformers：检索与重排](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)、[Google：推荐系统检索、评分和重排](https://developers.google.com/machine-learning/recommendation/overview/types)、[Milvus：混合检索排序](https://milvus.io/docs/v2.4.x/reranking.md)。

### 【1.4】ReAct、Agent Loop 与 Workflow

#### 【1.4.1】面试过程：约 06:43–08:47

**问题：** ReAct / Agent Loop 和 Workflow 有什么区别？

**当时回答的有效部分：** 描述了模型决定是否调用工具，拿到结果后继续判断；也提到 Workflow 由开发者编排。

**需要补强：** Workflow 也能有条件、循环、模型和人工节点；主要区别是流程的关键决策由模型动态选择，还是由程序预先规定。两者可以组合。

#### 【1.4.2】ReAct 的 What、Why、How

ReAct（Reasoning + Acting）让模型的决策与对外行动交替：根据已有信息选择行动 → 执行工具 → 观察结果 → 再决定继续还是回答。例如“望舒行动”先检索到标题，再读取附近原文并组织答案。

它适合需要访问外部数据、依据中间结果选择下一步的任务；代价是模型轮次、工具调用、延迟和异常处理增加。现代工具调用不要求把内部推理文本显示给用户；这里的决策是对行为的概括。

ReAct 描述推理与行动协作的思路；Agent Loop 是运行时反复调用模型、执行工具、返回结果的机制。一个 Agent Loop 不一定必须采用某一种固定的 ReAct 提示格式。[ReAct 原论文](https://arxiv.org/abs/2210.03629)

#### 【1.4.3】Workflow 和 Agent Loop 怎样选择

| 维度 | Workflow | Agent Loop |
| --- | --- | --- |
| 控制下一步 | 程序规定步骤和流转规则 | 模型依据上下文选择工具或结束 |
| 流程形态 | 固定路径，也可有分支、循环、重试和人工审批 | 动态调用工具，次数和路径可能变化 |
| 适合 | 必须执行特定步骤、重视可预测性 | 需要探索、工具选择和根据观察调整 |
| 代价 | 设计不充分时适应性有限 | 多轮调用增加延迟、成本和不确定性 |

**结合项目：** 如果每次都必须查知识库，可由 Workflow 强制先检索；然后进入 Agent 节点，让模型决定是否需要打开原文。项目聊天 Agent 由 LangChain `create_agent` 装配，底层通过 LangGraph 执行模型和工具的循环。

**面试表达：** Workflow 由开发者明确控制流程，Agent Loop 让模型动态选择行动；两者并不互斥。我的项目中模型能够检索后继续读取原文，但如果业务要求每轮都基于最新知识库，就应在程序流程中强制检索。

### 【1.5】Agent Loop 的终止条件

#### 【1.5.1】面试过程：约 08:47–11:02

**问题：** ReAct / Agent Loop 何时停止？代码里如何判断？

**当时回答：** 从语义上提到模型认为证据足够后回答；被追问代码条件时，尝试用置信度阈值和回答与问题的余弦相似度解释。

**应改进：** 将“模型决定不继续调用工具”的语义，落到 response 是否含待执行 tool calls 的协议和代码判断。置信度评分可以是业务额外设计，不能当作 Agent 循环的通用机制；回答复述问题时相似度可能高，但并没有提供答案。

#### 【1.5.2】正常结束与限制条件

```text
模型 response
  ├─ 有 tool_calls → 校验与执行工具 → 追加工具结果 → 再调模型
  └─ 无 tool_calls → 检查输出状态 → 返回最终回答
```

若 response 空、被截断或协议出错，运行时还需要对应处理。工具执行失败时可根据策略把错误反馈给模型，也可终止；一次 response 可能包含多个工具调用。

**示意伪代码，非项目原样源码：**

```python
while within_budget() and not cancelled():
    response = await model.invoke(messages, tools=tools)
    messages.append(response)

    if not response.tool_calls:
        return validate_final_response(response)

    for call in response.tool_calls:
        result = await execute_with_validation(call)
        messages.append(tool_message(call.id, result))

return stopped_result()
```

**常见限制：** 总超时、单工具超时、图执行步数、工具调用总次数、失败次数、用户取消、Token / 成本预算、人工审批等。达到限制后的行为由系统设计：可能终止、返回错误、暂停审批或输出受限结果。

项目 `BaseAgent` 将 `max_execution_steps` 传为 LangGraph `recursion_limit`，聊天图还配置工具错误处理、网络重试与权限 middleware。图步数、模型调用次数和工具调用次数是不同计数，不能直接等同。见 [运行配置](D:/Projects/Yuxi-Know/backend/yuxi/modules/agents/runtime/base.py) 与 [聊天图装配](D:/Projects/Yuxi-Know/backend/yuxi/modules/agents/runtime/agent_backends/chatbot/graph.py)。

**面试表达：** 模型返回工具调用时，运行时执行工具、追加结果并再次调用模型；模型返回最终内容且没有待执行工具时结束本轮。再结合最大步数、超时、调用次数和取消等机制控制运行。证据充分性可以额外评估，不能假设存在统一的置信度。

#### 【2.2.2】论文和 Agent 的追问准备

**论文怎么与 RAG 联系？** 可以说：测试阶段的记忆模块受到查询重写中“改善检索输入、提高召回”的思路启发，然后解释自己实际如何构造和使用记忆。回答时围绕“问题是什么 → 方法怎么做 → 为什么有帮助 → 实验观察”展开。

**MLP 和 SwiGLU 有什么关系？** 它们都是网络中用于特征变换的前馈结构。MLP 一般由线性层和非线性激活组成；SwiGLU 使用门控，一路变换后的信号控制另一路的信息传递。讲论文时先说明这些结构与本人研究的联系，再按追问深入。

**Plan-and-Execute 与 ReAct：** 前者强调形成计划并按计划执行；后者让模型结合已有信息，交替决定行动、观察工具结果并继续决策。两种方式可以结合：先形成总体计划，执行具体步骤时再利用工具反馈调整。

**Agent harness 是什么？** 可以把它理解为承载 Agent 运行的一套程序：组织模型调用、工具执行、状态、提示、权限和运行控制。模型决定下一步调用什么工具，harness 提供调用工具、返回结果、记录状态和限制执行的机制。

### 【2.4】部署后代码更新：热更新、重启和重建

**面试官问：** 项目部署过吗？部署后代码更新怎么办？怎么重建容器？

**当时回答：** 本地用 Docker 部署过；前端通过 Vue、Vite 热更新，后端代码和 `.env` 更新需要重建容器；重建使用 Docker Compose。

**项目中的具体过程：** [docker-compose.yml](../docker-compose.yml) 将前端源码挂载到容器，并运行 Vite 开发服务；普通前端源码修改后，Vite 检测变化并更新页面。后端 `backend/yuxi` 同样挂载给 API 和 worker，文件修改后容器可见，但当前 API 和 worker 启动命令没有配置自动重载，运行中的 Python 进程通常需要重启。`.env` 中注入到容器的环境变量在容器创建时确定，修改后需要重建相关容器。依赖或 Dockerfile 变化，则涉及镜像重新构建。

| 变化 | 执行机制 | 常见处理 |
| --- | --- | --- |
| 前端已挂载源码 | Vite 监听文件并更新开发页面 | 保存源码，观察热更新 |
| 后端已挂载源码 | 文件已变化，运行中的进程仍需重新加载 | 重启受影响的 API 或 worker |
| 容器环境变量 | 环境变量在创建容器时注入 | 重建受影响的容器 |
| Dockerfile、镜像依赖 | 镜像内容需要更新 | 构建镜像，再创建或更新容器 |

**三个动作怎样区分？** 重启是停止并重新启动已有容器里的进程；重建容器是按当前配置创建新的容器；构建镜像是根据 Dockerfile 生成新的镜像。容器使用镜像运行，同一个镜像可以用来创建多个容器。

```bash
# 后端挂载源码改变后，重启相关服务
docker compose restart api worker

# 配置影响 API 和 worker 时，按当前配置重建这两个容器
docker compose up -d --no-deps --force-recreate api worker

# 需要更新镜像内容时，构建并启动相关服务
docker compose up -d --build api worker
```

上述是针对 API 和 worker 的示例；如果 `.env` 的改动影响了数据库、前端等其他服务，也要处理对应服务。`docker compose restart` 不会将新的容器环境变量注入旧容器；`docker compose up` 可以依据配置或镜像变化创建、更新容器。参考 [Docker restart](https://docs.docker.com/reference/cli/docker/compose/restart/) 和 [Docker compose up](https://docs.docker.com/reference/cli/docker/compose/up/)。

**面试表达：**

> 我在本地用 Docker Compose 部署过项目。前端源码挂载进容器，由 Vite 监听修改并热更新；后端源码也挂载进容器，但当前没有自动重载，所以改完代码通常重启相关服务。环境变量发生变化时，我会重建受影响的容器；如果改的是依赖或 Dockerfile，就重新构建镜像并更新容器。

### 【2.5】项目管理平台：从阶段划分到业务闭环

**面试官问：** 如果让你做项目管理平台，怎样管理项目各个阶段？

**当时回答：** 按项目开发过程划分需求分析、架构设计、代码实现和评审等阶段，对不同节点进行针对性管理。

这个回答已经给出了项目阶段。继续展开时，重点讲每个阶段的**负责人、任务、产出、完成条件和进度**，让项目经理知道项目到了哪里、谁在处理、什么事情卡住了。

#### 【2.5.1】每个阶段具体管什么

| 阶段 | 要管理的内容 | 可观察的产出 |
| --- | --- | --- |
| 需求分析 | 需求内容、提出人、优先级、确认状态 | 确认后的需求及验收标准 |
| 架构设计 | 技术方案、负责人、方案评审和结论 | 设计方案与评审记录 |
| 开发实现 | 将需求拆成任务，记录负责人、进度和阻塞 | 完成的功能与关联代码变更 |
| 测试与评审 | 代码评审、测试结果、缺陷与修复 | 评审结论、测试结果和待处理问题 |
| 交付 | 上线时间、交付情况、遗留问题 | 交付记录和后续跟进事项 |

阶段完成条件可以让团队判断能否进入下一步。例如，需求阶段需要需求负责人确认范围与验收标准；尚未确认时，项目经理可以看到阻塞原因并安排处理。阶段状态的设置应和团队实际流程一起确定。

#### 【2.5.2】平台中的核心对象与业务流程

先建立项目、阶段、任务、人员四个基本对象：一个项目包含多个阶段，每个阶段包含任务；任务关联负责人、计划时间、状态和阻塞说明。项目首页展示当前阶段、关键里程碑、延期任务和负责人。点进项目后，可以追踪具体任务及其产出。

例如项目经理创建一个项目并设置需求、设计、开发、测试和交付阶段。需求负责人确认需求后，设计负责人提交方案并发起评审；开发任务按需求拆给成员；测试发现缺陷后关联回任务，由负责人处理；最后记录交付结果。期间如果某任务延期，项目经理能看到延期原因、负责人和更新后的计划。

对于开发板定制项目，还可以和业务人员一起梳理客户需求、硬件方案、物料采购、生产、测试与交付的实际节点，再将软件任务与相关节点关联。采购是否按时到货，会直接影响后续生产和交付；平台需要让跨部门的依赖关系和阻塞对项目负责人可见。

**第一版先做什么？** 先把创建项目、配置阶段、分配任务、更新状态和查看阻塞做成可用闭环；团队开始使用后，再根据实际痛点增加采购销售系统关联、报表或 Agent 辅助总结等能力。

**面试表达：**

> 我会先把项目划分为需求分析、架构设计、开发、测试评审和交付几个阶段。每个阶段明确负责人、任务、计划时间、产出和完成条件。平台首页让项目经理看到项目处于哪个阶段、有没有延期、哪些任务被阻塞。比如需求确认后进入方案设计，方案评审通过再拆分开发任务，测试发现的问题关联回具体任务。第一版先把项目、阶段、任务和进度串起来，再根据团队的实际流程扩展。如果管理的是开发板定制项目，我会进一步了解采购、生产和交付的节点，让跨部门依赖也能被跟踪。

### 【2.6】Git 协作：Pull Request 为什么叫 Pull

**面试官问：** 和朋友通过 GitHub 开发游戏，知道 Pull Request 吗？为什么叫 Pull Request，而不是 Push Request？

**当时回答：** PR 是 fork 代码后，新增或修改功能，向主分支提出提交申请。关于名称，当时理解为自己的云端仓库已有更新，但不清楚主分支现状，所以要 pull 过来分析 diff 和兼容性，再进行合并前检查。

**正确理解：** Pull Request（PR）是提出把一个分支的改动合并到另一个分支，并围绕改动进行讨论、检查和审查。名字可以从接收方的角度理解：“请项目维护者把我这一分支的改动拉过去并合并。”

```text
在功能分支开发 → 提交并推送到远程分支 → 发起 PR
→ 查看差异、讨论和检查 → 维护者决定是否合并到目标分支
```

比如和朋友合作游戏，你在功能分支完成背包功能并发起 PR，朋友可以看代码改动、提出问题、运行检查，通过后合并进团队的主分支。fork 后可以提 PR，同一仓库里的两个分支之间也可以提 PR。`push` 是把本地提交推送到远程仓库的动作；PR 是向目标分支提出合并请求及协作讨论的过程。参考 [GitHub：About pull requests](https://docs.github.com/en/pull-requests/get-started/about-pull-requests)。

**面试表达：**

> PR 是我完成一个功能后，请维护者把我的分支改动合并到目标分支。叫 pull request，可以理解为我请求对方拉取并接收我的改动。PR 还提供了看差异、代码审查和检查的地方，团队确认之后再合并。
